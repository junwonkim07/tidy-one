# Existing open-source "personal AI search / second brain / memory" products: adopt vs build

Scope: products that index a person's files, notes and memories across devices and expose them to AI models. The fit is judged against this user: a Korean solo developer with a MacBook (Apple Silicon), an iPhone and a Windows laptop; a Vultr VPS (1 vCPU / 2 GB, Ubuntu 24.04) already running Basic Memory behind mcp-auth-proxy for claude.ai web and mobile; clients are Claude Code, Codex, Aside, claude.ai web/mobile and possibly ChatGPT.

Method note: stars, last push, license and latest release were pulled from the GitHub REST API (`gh api repos/...`) on **2026-10-10**. Where a repo had no "latest release" object, the most recent tag or commit date is given instead. README and docs facts come from the repos' raw READMEs fetched the same day, unless another source is linked.

## Candidate-by-candidate evaluation (the evaluation table)

### Takeaway
Of ~35 projects checked, none combines (a) a per-device agent on macOS, Windows and iOS, (b) one central index that fits a 2 GB VPS, (c) a remote MCP server with OAuth usable from claude.ai web/mobile, and (d) good Korean embeddings by default. Each candidate covers one or two of these. Most of the full-stack "second brain" servers (Khoj, Onyx, Nextcloud Context Chat, Immich) need 6–12 GB RAM, and most ship English-only default embedding models.

### Inferences
- Korean is the common weak spot. Defaults are English-only in Khoj (`gte-small`), Basic Memory (`bge-small-en`), Supermemory local (`bge-base-en-v1.5`) and qmd (embeddinggemma, "limited" CJK). All four can be reconfigured to a multilingual model: multilingual-MiniLM or e5 in Basic Memory, Qwen3-Embedding-0.6B in qmd. Whatever the user adopts, they must override the embedding model, and in Basic Memory and Nextcloud Context Chat that means a full reindex.
- The 2 GB VPS rules out hosting any "full" central indexer (Khoj 8 GB, Onyx 10 GB, Context Chat 12 GB, Immich 6 GB). The VPS can host an MCP front-end, auth and a small SQLite/sqlite-vec index. Heavy embedding work belongs on the Apple Silicon Mac.
- Licensing traps: Screenpipe is now source-available, free only for personal non-commercial use. The Supermemory self-host server is closed-source. The Smart Connections license is non-OSI. Open WebUI has a branding clause. For a personal setup, Screenpipe's terms are acceptable if use stays non-commercial. The user is a developer at a company (company), so work use could count as commercial; flag this.
- Abandonment risk: Reor and obsidian-mcp-tools are archived; mem0 removed OpenMemory; Khoj appears to be in maintenance mode while its team builds Pipali and Open Paper; OpenRecall is stale.

## Is there one project that already does "per-device agent + central index + MCP for any AI client" well enough to adopt instead of building?

### Takeaway
No. As of Oct 2026, no open-source project offers per-device collectors on macOS, Windows and iOS, plus one central index, plus a remote OAuth MCP server, in a form that fits a 2 GB VPS and handles Korean well. The closest options each miss a core piece. **Khoj** has device sync clients but no MCP server, an 8 GB footprint and slowing development. **Nextcloud + nextcloud-mcp-server** has excellent multi-device sync and OAuth MCP, but its semantic layer is either experimental (Qdrant + Ollama) or heavy (Context Chat, 12 GB). **Onyx** has a central index and an MCP server but is team/SaaS-connector-oriented and needs 10 GB. **Screenpipe** has a per-device agent and MCP, but each device's index stays local and the license is commercial. The practical path is to *compose and build a thin layer*, not adopt one product.

### Cited Findings
- Khoj has the most complete "device agent → central server" pattern (desktop, Obsidian, Emacs and Android clients plus WhatsApp) ([src/interface](https://github.com/khoj-ai/khoj/tree/master/src/interface), [README](https://github.com/khoj-ai/khoj)). But it acts only as an MCP *client* ([mcp.py](https://github.com/khoj-ai/khoj/blob/master/src/khoj/processor/tools/mcp.py)). Users are still asking for a documented MCP server endpoint in July 2026 ([#1364](https://github.com/khoj-ai/khoj/issues/1364)). Its last release is a March 2026 beta (2.0.0-beta.28, GitHub API).
- Onyx exposes an MCP server for Claude Code and Codex and has a desktop app ([README](https://github.com/onyx-dot-app/onyx)). Its indexing edition needs 4 vCPU and 10 GB RAM minimum, and the 2 GB "Lite" edition cannot index documents ([docs](https://docs.onyx.app/deployment/getting_started/resourcing)).
- nextcloud-mcp-server provides streamable-HTTP MCP with OAuth for clients, 110+ tools and WebDAV file access, plus "experimental" semantic search needing Qdrant + Ollama ([repo](https://github.com/cbcoutinho/nextcloud-mcp-server)). Nextcloud's own Context Chat has no MCP and needs ≥12 GB RAM on CPU ([docs](https://docs.nextcloud.com/server/latest/admin_manual/ai/app_context_chat.html)).
- Screenpipe ships an MCP server and runs on macOS, Windows and Linux, but capture history "stays on your device by default". Cross-device sync is a paid Business-plan feature, and source builds are under a commercial license ([README](https://github.com/screenpipe/screenpipe), [LICENSE.md](https://github.com/screenpipe/screenpipe/blob/main/LICENSE.md)).
- Basic Memory, which the user already runs, is MCP-native and fits the VPS. Its Cloud tier adds web/mobile/desktop with bidirectional sync for $15/mo, but it covers Markdown notes, not arbitrary device files ([README](https://github.com/basicmachines-co/basic-memory)).
- Supermemory looks like a fit (memory + connectors + MCP), but self-hosted mode excludes both the MCP server and connectors, and the self-host binary is closed-source ([self-host docs](https://supermemory.ai/docs/self-hosting/overview)).
- OS-native indexes are not a cross-device answer. Windows' semantic file search via MCP is preview-only, Copilot+ only and local to that PC ([Learn](https://learn.microsoft.com/en-us/windows/ai/mcp/file-connector)). Recall export is EEA-only ([Microsoft Support](https://support.microsoft.com/en-US/Windows/Ai/Ai-Features/export-recall-snapshots)). Apple has not announced developer access to the Apple Intelligence semantic index ([Apple Newsroom](https://www.apple.com/newsroom/2026/06/apple-aids-app-development-with-new-intelligence-frameworks-and-advanced-tools/)).

### Inferences
- claude.ai web/mobile (and ChatGPT) can only reach **remote** MCP servers over HTTPS. Per-device stdio servers (Spotlight, Everything, filesystem, Screenpipe, qmd stdio) therefore serve only local clients (Claude Code or Codex on that machine) unless tunneled. So "reachable from any client" requires one central remote endpoint, which is the VPS. The device side should *push* content or extracts to it rather than expect the VPS to reach into devices.
- The best-fit architecture, inferred from the above:
  1. Keep Basic Memory on the VPS as the memory/notes hub and switch it to a multilingual embedding model.
  2. Add a light central "file catalog + extracts" index, either qmd-style SQLite (BM25 + sqlite-vec) or Basic Memory itself. Run embedding on the Mac rather than the 1 vCPU VPS.
  3. Run small per-device collectors that push text extracts and metadata.
  4. Expose everything through the existing mcp-auth-proxy.
- Adopting Nextcloud is the main "buy instead of build" alternative for the *sync* layer, with official clients on all of the user's OSes. Its AI/search layer, however, would still be either the experimental Qdrant + Ollama path or a 12 GB Context Chat box. Neither fits the current VPS.

### Gaps
- No primary-source head-to-head (reviews or benchmarks) of these products for multi-device personal use in 2026 was found. Most 2026 "comparison" posts are SEO or competitor blogs (e.g., luci.memories.ai, screenpi.pe).
- Whether Nextcloud server alone (files only, no Context Chat) runs acceptably on 1 vCPU / 2 GB alongside Basic Memory was not verified.

## Which pieces are best borrowed (sync clients, capture, per-device MCP, gateways)?

### Takeaway
Borrow these components, and keep the user's own glue thin:
- **qmd** as the retrieval engine pattern (BM25 + vector + rerank in SQLite, HTTP MCP), configured with Qwen3-Embedding for Korean.
- **Basic Memory** (already running) as the memory/notes MCP.
- **Screenpipe's MCP** for screen/audio history on the Mac and Windows laptop (personal, non-commercial use only).
- **Everything-based MCP** on Windows and **mdfind/Spotlight MCP** on macOS for instant local filename/content lookup by local agents.
- **Nextcloud desktop/iOS clients or Syncthing (Synctrain on iOS)** for moving files.
- **Paperless-ngx v3** if scanned documents and PDFs are in scope.
- **Immich's multilingual CLIP choice** (nllb/xlm) as the model pattern if photos are in scope, hosted off the VPS.
- **supergateway or mcp-proxy** to bridge any stdio server behind mcp-auth-proxy.

### Cited Findings
- qmd's HTTP MCP mode (`qmd mcp --http`, Streamable HTTP at `/mcp`, plus REST `/query` and `/metadata`) keeps models loaded across requests. The README explicitly recommends `Qwen3-Embedding-0.6B` for CJK. The total model footprint is ~2 GB: 300 MB embedder, 640 MB reranker and 1.1 GB query-expansion model ([README](https://github.com/tobi/qmd)).
- Basic Memory's own benchmark, which includes Korean, shows multilingual MiniLM cutting negative false positives from 0.75 to 0.00 and raising cross-language recall@5 to 1.00 versus the default `bge-small-en` ([benchmark](https://github.com/basicmachines-co/basic-memory/blob/main/docs/multilingual-embedding-benchmark.md)).
- Screenpipe: `claude mcp add screenpipe -- npx -y screenpipe-mcp@latest`; REST API on `localhost:3030`; SQLite FTS5; app/window allow and deny lists (`allow-apps`, `deny-apps`, `deny-windows`); accessibility tree first, OCR fallback ([README](https://github.com/screenpipe/screenpipe)).
- The Windows File Explorer MCP connector offers `search_files` with snippets and Office/PDF text reading, with semantic search on Copilot+ PCs. It is preview, on-device only, and permission-gated ([Learn](https://learn.microsoft.com/en-us/windows/ai/mcp/file-connector)).
- Everything/Spotlight MCP wrappers exist but are small or stale: mamertofabian (365★, last release 2024-12), elis132 (25★), spotlight-mcp (2★) ([mamertofabian](https://github.com/mamertofabian/mcp-everything-search), [elis132](https://github.com/elis132/everything-mcp), [adamrdrew](https://github.com/adamrdrew/spotlight-mcp)).
- nextcloud-mcp-server shows how to put OAuth in front of a file hub's MCP and how to exclude sensitive files via tags (`EXCLUDED_TAGS`) ([repo](https://github.com/cbcoutinho/nextcloud-mcp-server)).
- Syncthing on mobile is fragile: the official Android app was discontinued in Dec 2024, and the iOS options are the paid Möbius Sync (lagging) or the newer Synctrain ([forum](https://forum.syncthing.net/t/discontinuing-syncthing-android/23002), [Manual do Usuário](https://manualdousuario.net/en/basicsync-android-synctrain-ios-syncthing-apps/)).
- Paperless-ngx v3 now has built-in AI (Ollama embeddings, sqlite-vec vector store, document chat, LLM language setting), which makes paperless-ai largely redundant ([v3.0.0 notes](https://github.com/paperless-ngx/paperless-ngx/releases/tag/v3.0.0), [paperless-ai](https://github.com/clusterzx/paperless-ai)).
- Immich multilingual CLIP: `nllb` models suit searching in the user's native non-English language, and `xlm`/`siglip2` suit mixed-language queries ([Immich search docs](https://v1.124.0.archive.immich.app/docs/features/searching)). Immich needs 6 GB RAM, or 4 GB with ML off ([requirements](https://docs.immich.app/install/requirements)).
- Gateways: supergateway (v4.1.0, 2026-09-30) and mcp-proxy (v0.12.0) are active. IBM ContextForge (v1.0.11) is the most enterprise-grade. metamcp's last release was 2025-12, and mcp-auth-proxy's last release was 2026-05 (GitHub API data in table H above).
- claude-mem (98.9k★) shows strong demand for automatic coding-session capture via hooks across Claude Code, Codex and Cursor, storing to local SQLite + FTS5 with optional cloud sync ([README](https://github.com/thedotmack/claude-mem)). It is a pattern for the "memories" input stream that could feed Basic Memory.

### Inferences
- For a Korean user, the embedding choice matters more than the product choice. Standardize on one multilingual model across Basic Memory, qmd and any file index (multilingual MiniLM or e5 for small footprint, Qwen3-Embedding-0.6B for quality) so vectors and recall behave consistently.
- iPhone is the weakest device for "agents". No OSS project offers an iOS background indexer. Realistic iOS inputs are the Files/Photos upload clients (Nextcloud, Immich, Synctrain) and share-sheet capture (Karakeep has iOS and Android apps). iOS is a *source* that uploads, not a place that runs an index.
- On Windows, the Everything + MCP path works today on any PC. The first-party ODR File Explorer connector is worth watching but should not be relied on: it is preview, semantic search needs Copilot+, and third-party host access is unclear.
- Screenpipe is the only mature capture layer after Rewind's shutdown. Use it per device via local MCP, and optionally push daily summaries or extracts (not raw frames) into Basic Memory so claude.ai mobile can see them.

### Gaps
- No practical reports were found of running qmd's full pipeline on a 1 vCPU / 2 GB VPS, or of running qmd on Windows.
- Whether Karakeep's MCP supports remote HTTP plus OAuth was not checked.
- Korean OCR quality for Screenpipe (Apple Vision / Windows OCR), and Tesseract `kor` in Paperless, was not benchmarked in any source found.
