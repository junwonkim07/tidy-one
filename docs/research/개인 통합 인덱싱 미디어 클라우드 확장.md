# 모든 자료를 텍스트와 시각 벡터로 통일하라

**tidy-one을 일반 파일 전체로 넓히는 가장 단단한 설계는 "모든 자료를 맥에서 한국어 텍스트로 바꾸고, 픽셀만 따로 시각 벡터로 남기는 것"이다.** 문서 본문, 사진 속 글자(OCR), Apple이 사진에 붙여 둔 라벨과 장소, 영상의 음성 전사, 노션·구글·Plaud 본문은 모두 같은 텍스트 청크가 된다. 이 청크는 Kiwi 형태소 FTS와 1024차원 한국어 텍스트 벡터(bge-m3 또는 KURE-v1)로 색인된다. 사진과 영상 키프레임만 768차원 SigLIP2 시각 벡터를 하나 더 가진다. 검색은 하나의 카탈로그와 하나의 `search` 도구 안에서 이 세 신호를 RRF로 합친다. 텍스트·이미지·영상을 한 공간에 넣는 Qwen3-VL-Embedding-2B가 2026년 1월에 나왔지만, 2B 모델을 4GB CPU 서버의 질의 인코더로 쓰기는 어려워 맥 쪽 선택 기능으로만 둔다. 무거운 일은 모두 M2가 맡는다. 사진은 osxphotos로 Apple이 이미 계산한 라벨·OCR·캡션을 iCloud 다운로드 없이 읽는다. 영상은 Qwen3-ASR-1.7B(8비트)와 2~3초 간격 키프레임으로 처리한다. 클라우드 자료는 맥의 얇은 폴러(Notion PAT, `gws`의 Drive `changes`·Gmail `history`, Plaud CLI)가 가져온다. 서울 4GB 서버에는 두 텍스트 인코더(한국어 텍스트용 int8 약 0.6GB, SigLIP2 텍스트 타워 int8 약 0.3GB, 모두 추정)와 SQLite 카탈로그만 상주시킨다. 그러면 1GB 이상 여유가 남지만, 이 수치를 실측하는 것이 첫 관문이다. Onyx(최소 10GB), Immich(6GB), 2026년 8월 보관 처리된 Airweave 같은 완제품은 서버에 올릴 수 없으니 코드와 설계만 빌린다. 가장 큰 위험은 기술이 아니라 정책이다. Slack API 약관은 메시지 대량 내보내기를 막고, Data Access API로 만든 영구 색인도 금지한다. 그래서 Slack은 색인하지 않고 클라이언트의 Slack 커넥터에 맡기며, 얼굴·신분증·회의 원문은 기기 밖으로 내보내지 않는다.

## 하나의 카탈로그, 세 개의 신호: 결국 모든 자료는 텍스트가 된다

네 종류의 자료에서 "검색할 수 있는 내용"을 뽑아 보면 공통분모가 드러난다. 문서와 클라우드 작업물은 원래 텍스트다. 사진에서 검색되는 정보는 대부분 OCR 글자, 장소, 날짜, 인물 이름, Apple이 붙인 장면 라벨처럼 텍스트로 바꿀 수 있다. 영상도 음성 전사, 화면 녹화의 OCR, 키프레임 캡션이 핵심 정보를 담는다. **텍스트로 바꿀 수 없는 것은 "어떻게 보이는가"를 담은 픽셀뿐이다.** 그래서 색인은 한 개의 카탈로그에 두 개의 벡터 공간을 두는 형태가 된다. 모든 종류가 공유하는 한국어 텍스트 공간이 하나, 사진과 영상 프레임만 쓰는 시각 공간이 하나다. 이렇게 하면 이전 조사에서 정한 한국어 임베딩과 형태소 검색이 사진·영상·클라우드에도 그대로 적용된다. 한국어 품질을 올리는 작업 하나가 모든 종류의 검색 품질을 함께 올린다.

"하나의 모델로 전부"라는 대안도 처음으로 현실성이 생겼다. **Qwen3-VL-Embedding**(Apache-2.0, 2B·8B)은 텍스트, 이미지, 스크린숏, 영상을 30개 이상의 언어로 한 공간에 넣는다. 차원은 Matryoshka 방식으로 64~2048 사이에서 고를 수 있다. MMEB-V2 영상 검색 점수는 2B가 53.9로, 이전 세대 공개 모델(VLM2Vec-2B 20.6, VLM2Vec-V2 28.8, GME-7B 28.4)을 크게 앞선다 ([HF 모델 카드](https://huggingface.co/Qwen/Qwen3-VL-Embedding-2B), [GitHub](https://github.com/QwenLM/Qwen3-VL-Embedding)). 하지만 의미 검색은 질의를 문서와 같은 모델로 임베딩해야 성립한다 ([Immich searching](https://github.com/immich-app/immich/blob/main/docs/docs/features/searching.md)). claude.ai는 서버로만 들어오므로 그 2B 모델을 4GB CPU 서버에서 질의마다 돌려야 하는데, 크기와 속도 모두 무리다(추론). 한국어 텍스트 검색에서 KURE 계열과 비교한 결과도 없다. 반면 SigLIP2는 Immich가 텍스트 타워와 이미지 타워를 별도 ONNX 파일로 배포한다 ([Immich HF](https://huggingface.co/immich-app/ViT-B-16-SigLIP2__webli/tree/main)). 이미지 타워는 맥에, 텍스트 타워는 서버에 나눠 올릴 수 있다는 뜻이다. 그래서 중앙의 시각 색인은 SigLIP2로 하고, Qwen3-VL-Embedding은 맥에서 영상 구간 벡터를 만드는 선택 기능으로 둔다.

시각 벡터만으로 끝내지 않는 이유는 한국어 격차다. Immich의 Crossmodal-3600 평가에서 SigLIP2 ViT-B/16의 한국어 재현율은 **71.09%로, 영어 84.86%보다 14점 낮다** ([Immich docs](https://docs.immich.app/features/searching)). 이 격차는 OCR, 라벨, 장소, 캡션 같은 텍스트 신호와 하이브리드로 합치면 줄어든다. 날짜와 장소는 임베딩보다 구조화된 필터로 다루는 편이 낫다. 호출하는 LLM이 "작년 제주 바다 사진"을 `{date: 2025, place: "제주", query: "바다"}`로 나눠 도구 인자에 넣게 하면 된다(추론).

| 종류 | 발견·변경 감지 | 텍스트로 바꾸는 방법 | 시각 벡터 | M2 처리 시간 (추정) | 중앙 저장량 (추정) |
|---|---|---|---|---|---|
| 문서 | FSEvents·Spotlight(맥), Everything·USN(윈도우) | markitdown, docling + ocrmac(accurate), kordoc | 없음 | 파일 수에 비례 | 청크당 1024차원 int8 약 1KB + 본문 |
| 사진 (3만 장 가정) | osxphotos `hexdigest`, FSEvents | Apple의 OCR·라벨·장소·캡션 재사용, 없을 때만 Vision OCR, 선택적 Qwen3-VL 캡션 | SigLIP2-B/16 768차원 | 메타데이터 수 분, 임베딩 10~30분, OCR 2~4시간 | 벡터 약 23MB + 텍스트 15~60MB |
| 영상 (3천 클립 + 회의 20시간 가정) | osxphotos `--only-movies`, FSEvents | Qwen3-ASR 전사, 대표 프레임 캡션, 화면 녹화 OCR | 키프레임별 SigLIP2 (+선택: Qwen3-VL 구간 벡터) | 밤 1~3회 | 분당 20~25KB, 합계 40~160MB |
| 클라우드 | Notion `last_edited_time`, Drive `startPageToken`, Gmail `historyId`, Plaud `created_at` | API 내보내기(Docs→Markdown), 블록 트리, 전사·요약 | 없음 | 노션 첫 백필 수십 분 | 본문 청크 |

처리 시간과 저장량은 아래 섹션의 측정치를 바탕으로 한 산술 추정이다. 사용자 라이브러리의 실제 규모는 아직 모른다.

## 종류별 파이프라인은 모두 맥에서 돌고, 서버에는 결과만 간다

네 종류 모두 같은 규칙을 따른다. 발견, 추출, OCR, 음성 인식, 임베딩은 M2에서 한다. 서버에는 메타데이터, 텍스트 청크, int8 벡터, 삭제 묘비만 인증된 수집 API로 밀어 넣는다. 원본, 썸네일, 얼굴 데이터, 회의 전사 원문은 기기에 남는다. 아래에서는 종류마다 무엇을 빌려 오고 어디가 함정인지만 정리한다.

### 문서: 이전 결론은 유지하고, OCR 모드와 구글 내보내기만 갱신한다

이전 조사의 결론은 대부분 그대로다. 마크다운과 코드는 그대로 읽고, DOCX·PPTX·XLSX는 **markitdown**(MIT), 텍스트 층이 있는 PDF는 pdfplumber나 docling으로 처리한다. 스캔 PDF와 이미지는 맥에서 docling의 `ocrmac`(Apple Vision `ko-KR`)으로, HWP·HWPX는 **kordoc**으로 변환한다 ([markitdown](https://github.com/microsoft/markitdown), [docling OCR](https://docling-project.github.io/docling/concepts/OCR/), [kordoc](https://dev.co/ai/mcp/kordoc)). 윈도우에서는 PP-OCRv5 한국어 인식 모델(약 14MB, 자체 데이터셋 정확도 88.0%)을 쓴다 ([PaddleOCR HF](https://huggingface.co/PaddlePaddle/korean_PP-OCRv5_mobile_rec)). 청크는 제목 경로를 먼저 따라 자른 뒤 Kiwi 문장 분리로 300~600 모델 토큰, 10~15% 겹침 창을 만든다. 텍스트 임베딩은 Ollama에서 바로 돌릴 수 있는 bge-m3를 첫 후보로, 품질이 우선이면 KURE-v1을 쓴다. MTEB-ko nDCG@10이 0.816으로 가장 높은 KURE-v2는 토큰당 다중 벡터라 sqlite-vec과 맞지 않는다 ([KURE-v2](https://huggingface.co/nlpai-lab/KURE-v2), [KURE](https://github.com/nlpai-lab/KURE)). 지금 쓰는 multilingual MiniLM은 한국어 금융 벤치마크 top-1 F1이 약 0.30으로 한국어 특화 모델(약 0.70~0.75)에 크게 뒤진다 ([AutoRAG](https://github.com/Marker-Inc-Korea/AutoRAG-example-korean-embedding-benchmark)). SQLite FTS5의 `unicode61`은 "검색엔진을" 같은 어절을 통째로 색인하고, `trigram`은 3글자 미만을 매칭하지 못한다. 그래서 Kiwi로 형태소를 분리한 별도 열이 필요하다 ([SQLite FTS5](https://www.sqlite.org/fts5.html), [WikiDocs](https://wikidocs.net/251980)).

이번 조사로 바뀐 점은 다음 표와 같다.

| 항목 | 이전 결론 | 이번 조사로 바뀐 점 |
|---|---|---|
| 서버 | 1 vCPU/2GB에 임베딩 모델 하나만 상주 | 4GB(2 vCPU)라 한국어 텍스트 인코더와 SigLIP2 텍스트 타워를 함께 둘 수 있음 (추정, 실측 필요) |
| 텍스트 임베딩 | bge-m3 우선, 품질은 KURE-v1 | 모델 선택은 그대로. OCR·전사·캡션·SaaS 본문까지 **모든 종류가 같은 텍스트 공간을 공유**하므로 모델 교체의 효과가 전 종류로 퍼짐 |
| 형태소 검색 | Kiwi 형태소 열 + 질의도 같은 방식으로 분석 | 그대로 주 열로 쓰고, OCR 텍스트와 파일명·식별자용 **trigram 보조 열**을 추가. OCR 오인식 글자는 형태소 분석을 깨뜨리기 때문. 2음절 질의는 여전히 Kiwi 열이 맡음 |
| OCR | docling + ocrmac(`ko-KR`) | Vision은 **accurate 모드에서만 한국어를 지원**하므로 모드를 강제. 사진 보관함은 Apple이 이미 한 OCR을 먼저 재사용. 표·영수증에는 WWDC25 `RecognizeDocumentsRequest` 검토 |
| Office·PDF | markitdown, docling | 그대로. 구글 네이티브 문서는 추출 대신 Drive API 내보내기 사용 |
| HWP | kordoc | 이번 조사에서 재검증하지 않음 |
| 청크 단위 | 제목 경로 우선, 300~600토큰 | 소스별 단위 추가: 노션 제목 블록, Gmail 스레드, 슬라이드 단위, Plaud·영상 전사는 30~60초 구간 |
| 재순위 | 맥 전용, 서버는 생략 또는 상위 5~10개 | 그대로 |

OCR 모드 차이는 숫자로 확인됐다. Vision 텍스트 인식 revision 3이 Live Text를 구동하며 한국어와 일본어를 추가했고, 지원 언어는 인식 수준에 따라 다르다 ([WWDC22 10024](https://developer.apple.com/videos/play/wwdc2022/10024/?time=117), [Apple Developer Forums](https://developer.apple.com/forums/thread/121048)). 이 맥(M2, macOS 26.2)에서 2026-10-10에 직접 돌린 시험에서 accurate 모드는 `["ko-KR","en-US"]`로 1600×1200 이미지의 한국어 줄을 모두 정확히 읽었고, 예열 뒤 장당 0.20~0.23초가 걸렸다. fast 모드는 0.06초였지만 한국어를 "2FOIE#E: EF-" 같은 깨진 문자열로 냈다. 이 시험은 깨끗한 합성 텍스트 한 장만 쓴 로컬 측정이라 공개 출처가 없다. 다만 fast 모드가 조용히 쓰레기 텍스트를 FTS에 넣는다는 위험은 분명하다. docling의 OcrMac 옵션도 "accurate"와 "fast"를 고를 수 있으므로 ([docling OCR](https://docling-project.github.io/docling/concepts/OCR/)) 설정에서 accurate를 명시해야 한다. WWDC25의 `RecognizeDocumentsRequest`는 줄을 문단으로 묶고 표와 목록을 읽으며 26개 언어를 지원한다 ([WWDC25 272](https://developer.apple.com/videos/play/wwdc2025/272/)). 한국어가 그 26개에 들어 있는지는 확인하지 못했다.

구글 네이티브 문서는 추출기를 거칠 필요가 없다. Drive API는 Docs를 `.md`로, Slides를 `.txt`로 직접 내보낸다. Sheets의 CSV 내보내기는 **첫 시트만** 나오므로 xlsx로 받아 markitdown에 넘기거나 탭마다 Sheets API를 부른다. 내보내기 크기는 10MB로 제한된다 ([Export MIME types](https://developers.google.com/workspace/drive/api/guides/ref-export-formats), [files.export](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/export)). Drive에 올린 일반 PDF·DOCX는 내려받아 위의 문서 파이프라인으로 보낸다.

### 사진: Apple이 이미 계산한 것을 다운로드 없이 읽는다

사진 파이프라인의 핵심 부품은 **osxphotos**(MIT, v0.77.2, 2026-09-27)다. 사진 앱의 SQLite와 검색 색인을 직접 읽고, macOS 27의 `leo.sqlite` 변경까지 따라가고 있다 ([osxphotos releases](https://github.com/RhetTbull/osxphotos/releases)). 이 라이브러리가 노출하는 정보는 대부분 Apple이 기기에서 이미 계산해 둔 것이다. 장면 라벨, 명명된 인물, 역지오코딩된 장소, 미학 점수, mediaanalysisd가 만든 AI 캡션(`ai_caption`)이 있다. `search_info`에는 장소명·수역·활동·장소 유형·이벤트·반려동물·랜드마크·문서 유형, 그리고 **사진 앱이 이미 추출한 OCR 텍스트(`detected_text`, macOS 13 이상)**가 들어 있다 ([API_README](https://rhettbull.github.io/osxphotos/API_README.html), [searchinfo.py](https://github.com/RhetTbull/osxphotos/blob/main/osxphotos/searchinfo.py)). 그래서 사진 색인의 1차 작업은 모델 없이 끝난다. Apple의 결과를 텍스트 청크로 바꿔 넣기만 하면 "영수증"이나 "화이트보드" 같은 질의의 상당수가 키워드와 텍스트 벡터로 잡힌다(추론). `search_info`는 photoanalysisd가 아직 돌지 않은 사진에는 비어 있을 수 있다. 그런 사진만 Vision accurate OCR로 보충한다.

iCloud "Mac 저장 공간 최적화"를 켜 둔 보관함도 문제가 되지 않는다. osxphotos는 원본이 디스크에 없는 사진을 `ismissing`으로 표시하고, 로컬에 남아 있는 미리보기 파생 이미지 경로를 해상도 순으로 `path_derivatives`에 돌려준다 ([API_README](https://rhettbull.github.io/osxphotos/API_README.html)). 저장 공간 최적화는 원본만 지우고 미리보기·썸네일은 남긴다 ([Mole blog, 2차 출처](https://mole.tw93.fun/blog/how-to-free-up-photos-storage-mac)). 따라서 `path_derivatives[0]`을 임베딩과 OCR 입력으로 쓰면 **iCloud 다운로드 0건**으로 색인할 수 있다. CLIP 계열은 입력이 224~384픽셀이라 미리보기 해상도로 충분하다. 작은 영수증 글씨만 원본이 필요할 수 있다. iCloud 사진을 쓴다면 아이폰으로 찍은 사진도 맥 보관함에 들어오므로, 아이폰에 색인기를 두지 않는다는 이전 결론과 충돌하지 않는다.

권한은 생각보다 단순하다. osxphotos 기반 apple-photos-mcp는 사진 보관함 SQLite가 보호 디렉터리에 있어 **전체 디스크 접근 권한(FDA)**이 필요하다고 밝힌다 ([apple-photos-mcp](https://github.com/sweetrb/apple-photos-mcp)). 반면 PhotoKit은 사진 TCC 권한 프롬프트를 띄워야 하는데, launchd가 실행한 명령줄 도구는 프롬프트 없이 조용히 거부된다 ([Apple Developer Forums 106534](https://developer.apple.com/forums/thread/106534)). 그러니 색인에는 PhotoKit을 쓰지 않는다. 고정된 경로의 서명된 에이전트 바이너리에 FDA를 한 번 주면 사진 보관함, `~/Pictures`, `~/Desktop`, `~/Downloads`를 함께 읽는다(추론). 단, 바이너리 경로가 버전마다 바뀌면 업데이트 때마다 권한이 사라진다 ([claudeissues #74234](https://claudeissues.com/issue/74234-macos-full-disk-access-tcc-prompts-reappear-on-every-auto-update-per-version-bin)). PhotoKit은 나중에 사용자가 원본을 열어 달라고 할 때 `isNetworkAccessAllowed=true`로 원본을 받는 용도로만 남긴다 ([Apple docs](https://developer.apple.com/documentation/photos/phimagerequestoptions/isnetworkaccessallowed)). 사진 앱의 내부 DB는 macOS마다 바뀌므로 osxphotos 버전을 고정한다. 사진 색인기는 인터페이스 뒤에 두고, `search_info`를 못 읽을 때는 "파일 + EXIF + 자체 OCR·CLIP"으로 물러나게 한다.

시각 벡터 모델은 **SigLIP2 ViT-B/16(256px, Apache-2.0)**을 기본으로 한다 ([HF google/siglip2-base-patch16-256](https://huggingface.co/google/siglip2-base-patch16-256)). 아래 표에서 보듯 한국어 점수가 가장 높은 모델들은 라이선스나 크기에서 걸린다.

여기서 두 조사 노트의 판단이 갈렸다. 사진 노트는 nllb-clip-base를 한국어 품질 업그레이드 경로로 제안했지만, 영상 노트는 NLLB-CLIP이 **CC-BY-NC-4.0**임을 확인했다. 사용자가 company 업무에도 이 색인을 쓴다면 비상업 라이선스 모델은 피해야 한다. 그래서 업그레이드 경로는 Apache-2.0인 SigLIP2 L·SO400M으로 정한다. 문제는 크기다. SigLIP2의 텍스트 타워는 대부분 Gemma 어휘 임베딩 표가 차지한다(B/16 기준 약 282M 파라미터, 추론). 한국어용으로 어휘를 잘라 27.81% 줄인 커뮤니티 변형도 있지만 ([alphaedge-ai](https://huggingface.co/alphaedge-ai/siglip2-large-patch16-512-kor-16384)) 품질은 검증되지 않았다. 맥에서 이미지 타워를 돌릴 때는 Neural Engine보다 GPU를 쓴다. SigLIP2-SO400M Core ML을 ANE fp16으로 돌리면 상위 10개 결과의 겹침이 82%로 떨어져(GPU는 98%) 순위가 바뀐다 ([antonlnz](https://huggingface.co/antonlnz/siglip2-so400m-image-coreml)).

캡션은 선택적으로만 만든다. 작은 VLM 중 한국어 캡션을 낼 만한 것은 Qwen 계열이다. **Qwen3-VL-4B**는 Apache-2.0이고 32개 언어 OCR을 지원하며 ([HF](https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct)), mlx-vlm으로 맥에서 돈다 ([mlx-vlm](https://github.com/Blaizzy/mlx-vlm)). Florence-2는 영어 전용이다 ([HF](https://huggingface.co/microsoft/Florence-2-large)). M1 Max에서 Qwen3-VL-4B 3비트가 약 41 tok/s를 낸 측정이 있다 ([vllm-mlx](https://vllm-mlx.is-a.dev/benchmarks/image.md)). 기본 M2는 메모리 대역폭이 100GB/s라 ([Apple Newsroom](https://www.apple.com/newsroom/2022/06/apple-unveils-m2-with-breakthrough-performance-and-capabilities/)) 장당 5~10초가 걸릴 것으로 추정된다. 3만 장 전체를 캡션하면 40~80시간이다. 그러니 캡션은 스크린숏, 문서, 화이트보드, 그리고 Apple 캡션과 라벨이 없는 사진에만 밤사이 붙인다. 프롬프트는 "한국어 1~2문장 설명 + 영어 키워드"로 한 번에 받는다.

장소와 인물은 필터로 쓴다. 사진 앱 항목은 PlaceInfo와 `search_info`에 이미 역지오코딩된 지명이 있다. 일반 파일은 **krgc**로 한국의 시·도, 시·군·구, 읍·면·동을 오프라인으로 얻는다 ([PyPI krgc](https://pypi.org/project/krgc/)). 해외 지명용 reverse_geocoder는 2016년 이후 릴리스가 없다 ([GitHub](https://github.com/thampiman/reverse-geocoder)). 얼굴은 직접 임베딩하지 않는다. 사용자가 사진 앱에서 이름을 붙인 인물만 이름으로 저장한다. 중복은 SHA-256(정확한 중복)과 imagehash(BSD-2)의 pHash·dHash(유사 중복)로 묶는다 ([imagehash](https://github.com/JohannesBuchner/imagehash)). 바탕화면, 다운로드, iCloud Drive를 오가며 복사된 스크린숏이 결과 하나로 합쳐진다.

이 맥에 맞춰 3만 장을 가정하면 비용은 이렇다(산술 추정). 메타데이터는 수 분, 미리보기 디코딩은 5~15분이다. SigLIP2-B/16 임베딩은 10~30분인데, rclip이 M1 Max에서 5만 장을 7분에 처리한 수치가 상한 참고치다 ([rclip](https://github.com/yurijmikhalevich/rclip)). Vision OCR은 2~4시간이지만 Apple OCR이 있는 사진은 건너뛴다. 중앙에는 768차원 int8 벡터 약 23MB와 텍스트 15~60MB만 간다. 썸네일은 160px WebP로도 150~250MB라 기본으로 끈다. 빌려 올 것도 정리된다. Immich에서는 모델 후보표와 텍스트·이미지 ONNX 분리를, apple-photos-mcp(MIT, 기본 읽기 전용)에서는 필드 선택과 안전 기본값을, rclip에서는 SQLite 기반 증분 색인을 가져온다. Immich 서버 자체는 RAM 6GB 이상이 필요하고 ([Immich requirements](https://docs.immich.app/install/requirements)), 내장 OCR도 출시 당시 공식 지원 언어가 영어·중국어·일본어뿐이라 ([Immich v2.2.0](https://immich.app/blog/v2.2.0-release)) 그대로 쓰지 않는다.

### 영상: 키프레임보다 음성 인식이 먼저다

영상은 네 층으로 나눠 재시작 가능한 큐로 처리한다. **T0(메타데이터)**는 모든 영상에 적용한다. 사진 앱 영상은 osxphotos의 UUID와 라벨을 쓰고, `~/Movies`·`~/Downloads`의 일반 파일은 ExifTool이 읽는 QuickTime Keys(`location.ISO6709` GPS, 렌즈·기기 정보)를 쓴다 ([ExifTool](https://exiftool.org/TagNames/QuickTime.html)). 이 단계에서 종류도 나눈다. 카메라 제조사가 없고 "화면 기록" 파일명이면 화면 녹화, 10분이 넘고 화면이 대부분 정지해 있으면 회의·강의, 나머지는 휴대폰 클립이다. **T1(키프레임 + SigLIP2)**도 모든 영상에 적용한다. 5~60초짜리 단일 샷 클립은 장면 검출이 별 도움이 안 되므로 첫·끝 프레임과 2~3초 간격 프레임을 뽑고, 연속 프레임의 코사인 유사도가 0.95를 넘으면 버린다(추론). 긴 강의나 편집 영상에만 PySceneDetect(BSD-3, v0.7.1)나 ffmpeg의 `scene` 점수를 쓴다 ([PySceneDetect](https://github.com/Breakthrough/PySceneDetect), [ffmpeg](https://ffmpeg.org/ffmpeg-filters.html#select_002c-aselect)). Immich는 영상마다 미리보기 한 장의 임베딩만 계산한다 ([smart-info.service.ts](https://github.com/immich-app/immich/blob/main/server/src/services/smart-info.service.ts)). tidy-one은 키프레임마다 타임스탬프를 붙여 "IMG_1234.MOV 0:42"처럼 답하게 하는 것이 차별점이다.

**T2(음성)**은 음성이 있는 영상에만 돌리며, 회의·강의 녹화에서 가장 가치가 크다. 먼저 SenseVoiceSmall의 `nospeech` 태그나 VAD로 음성 유무를 거른다. SenseVoiceSmall은 한국어 언어 식별을 지원하고 Whisper-Large보다 15배 이상 빠르다고 밝힌다. 다만 모델 라이선스는 FunASR 자체 라이선스다 ([SenseVoice](https://github.com/FunAudioLLM/SenseVoice)). 전사는 **Qwen3-ASR-1.7B**(Apache-2.0, 2026-01-29)로 한다. 기술 보고서의 한국어 CER은 FLEURS 2.57, CommonVoice 5.88, 대화체 MLC-SLM 8.61이다 ([arXiv 2601.21337](https://arxiv.org/pdf/2601.21337)). 독립 측정도 같은 방향이다. M5 MacBook Air에서 MLX 8비트 Qwen3-ASR-1.7B는 FLEURS-ko CER 3.54%로 Whisper-large-v3-turbo(whisper.cpp)의 4.25%보다 낮았고, 속도도 9.6배 대 2.6배 실시간이었다 ([WhisperNotes](https://whispernotes.app/blog/qwen3-asr-vs-whisper)). 다른 순위표에서도 Qwen3-ASR-1.7B(4.60%)가 whisper-large-v3(4.89%)와 turbo(5.24%)를 앞섰다 ([Handy](https://models.handy.computer/languages/ko)).

**양자화 수준은 한국어에서 결정적이다.** 같은 모델의 FLEURS 한국어 WER은 4비트에서 19.95, 8비트에서 6.89였다. 영어는 6.57과 5.64로 거의 차이가 없었다 ([soniqo](https://soniqo.audio/benchmarks)). 그러니 **반드시 8비트**를 쓴다. 실행은 Qwen3-ASR을 포함한 mlx-audio(MIT)로 한다 ([mlx-audio](https://github.com/Blaizzy/mlx-audio)). 한 번에 최대 20분까지 받으므로 긴 회의는 나눠 넣는다. 대안은 mlx-whisper의 Whisper-large-v3-turbo다. 같은 파일에서 whisper.cpp보다 2배 빨랐고 ([billmill](https://notes.billmill.org/dev_blog/2026/01/updated_my_mlx_whisper_vs._whisper.cpp_benchmark.html)), Core ML 버전은 M2 MacBook Pro에서 10분 음성을 63초에 처리했다 ([WhisperNotes](https://whispernotes.app/blog/introducing-whisper-large-v3-turbo)). 이 수치들로 보면 기본 M2에서 1시간 회의의 전사는 6~12분이 걸릴 것으로 추정된다. 이 결과는 영상 밖에도 쓸모가 있다. 사용자의 기존 Plaud→Whisper→Notion 파이프라인도 같은 근거로 Qwen3-ASR 8비트로 바꿀 후보가 된다. 화자 분리가 필요한 회의는 WhisperX + pyannote community-1을 쓴다. 하지만 GPU 가속이 CUDA 전용이라 맥에서는 CPU로 돌고, Hugging Face 토큰과 모델 약관 동의가 필요하다 ([whisperX](https://github.com/m-bain/whisperX)).

**T3(캡션·OCR)**은 선택적으로 밤에 돌린다. SigLIP 클러스터의 대표(medoid) 프레임 1~3장에만 Qwen3-VL로 한국어·영어 캡션을 붙이고, 화면 녹화는 내용이 바뀐 프레임에만 Vision OCR을 돌린다. 마지막으로 전사와 캡션에서 한국어 1~2문장 요약을 만든다. Qwen3-VL-Embedding-2B의 구간 벡터(30초당 1개, Matryoshka 512~1024차원)는 "그 장면 나오는 클립" 같은 질의에 가장 좋은 공개 선택지다. 다만 SigLIP2-B보다 입력당 5~10배 무거우므로 맥 안의 선택 색인으로만 둔다(추론). MLX 8비트 포트가 있다 ([mlx-community](https://huggingface.co/mlx-community/Qwen3-VL-Embedding-2B-8bit)).

비용은 감당할 만하다(산술 추정). 40초 평균 클립 3천 개(약 33시간)에 회의·강의 20시간을 더하면 T1은 0.5~2시간, T2는 2.5~5시간, T3는 3~20시간이다. 전체 백로그는 전원을 연결한 M2에서 밤 1~3회면 끝나고, 이후 증분은 하루 수 초~수 분이다. 모델을 한 번에 하나씩 띄우면 최대 RAM은 SigLIP2 2~4GB, Qwen3-ASR 8비트 약 2.7GB, Qwen3-VL-4B 3~4GB로 24GB 안에서 넉넉하다. 중앙 저장량은 int8 기준 분당 20~25KB로, 위 라이브러리 전체가 40~160MB다. 이 숫자는 모두 다른 칩의 측정에서 외삽했으므로, 15분짜리 M2 마이크로 벤치마크로 바꿔야 한다.

두 가지 함정이 있다. 첫째, 이 맥에는 ffmpeg가 없다. 맥 에이전트는 처음에는 AVFoundation(프레임·메타데이터), Vision, osxphotos만으로 시작할 수 있다. ffmpeg나 PyAV는 이상한 코덱과 윈도우 에이전트용으로 나중에 넣는다(추론). 둘째, iCloud에만 원본이 있는 영상은 사진과 달리 미리보기로 대신할 수 없다. 음성과 프레임이 모두 원본에 있기 때문이다. 이런 영상은 T0와 Apple 라벨만 색인하고, 전원과 Wi-Fi가 있을 때 osxphotos `--download-missing`이나 PhotoKit으로 받아 처리하는 정책이 필요하다(추론, 조사 노트에서 다루지 않은 공백). 빌려 올 완제품은 없다. VideoRAG는 영어 환경에서만 시험됐고, 비상업 라이선스인 ImageBind와 RTX 3090을 전제로 한다 ([VideoRAG](https://github.com/HKUDS/VideoRAG), [ImageBind LICENSE](https://github.com/facebookresearch/ImageBind)). Edit Mind는 Docker가 Apple GPU를 쓰지 못한다고 스스로 밝히고 ([Edit Mind](https://github.com/IliasHad/edit-mind)), NVIDIA VSS는 Apple Silicon을 지원하지 않는다 ([VSS](https://github.com/NVIDIA-AI-Blueprints/video-search-and-summarization)). 가져올 것은 "영상을 텍스트(전사·캡션)로 바꿔 일반 텍스트 RAG로 색인하고, 시각 벡터는 두 번째 검색 경로로 둔다"는 VideoRAG의 구조뿐이다.

### 클라우드: 플랫폼 대신 맥의 얇은 폴러 네 개

"SaaS를 한 번에 연결해 주는" 오픈소스 플랫폼은 1인 4GB 환경에 맞지 않거나 2026년에 사라졌다. **Airweave**(MIT, 노션·슬랙·Gmail·Drive 모듈 보유)는 2026년 8월 29일 저장소가 보관 처리됐다. 조직의 다른 저장소도 모두 보관됐고, 이유나 후계 프로젝트는 밝히지 않았다 ([Airweave](https://github.com/airweave-ai/airweave)). **SurfSense**는 로컬 파일용 데스크톱 앱으로 방향을 틀었고, 클라우드 서비스의 데이터는 2026년 10월 18일에 삭제된다 ([SurfSense sunset](https://www.surfsense.com/sunset)). **Onyx**는 표준 배포에 최소 4 vCPU·10GB RAM·32GB 디스크가 필요하다. 1GB 미만으로 도는 Lite는 문서를 색인하지 못한다 ([Onyx resourcing](https://docs.onyx.app/deployment/getting_started/resourcing), [Onyx README](https://github.com/onyx-dot-app/onyx)). Nango는 무료 자체 호스팅에서 동기화 기능을 뺐다 ([Nango](https://nango.dev/docs/guides/platform/self-hosting.md)). PyAirbyte와 그 커넥터는 OSI 오픈소스가 아닌 ELv2이고 ([PyAirbyte](https://github.com/airbytehq/PyAirbyte)), Pipedream은 소스 공개 라이선스에 2025년 11월 Workday 인수 계약이 걸려 있다 ([LICENSE](https://github.com/PipedreamHQ/pipedream/blob/master/LICENSE), [Workday](https://en-sg.newsroom.workday.com/2025-11-19-Workday-Signs-Definitive-Agreement-to-Acquire-Pipedream?asPDF=1)). Composio, Nango Cloud, Paragon, Merge 같은 인증 중개 서비스는 "많은 최종 사용자의 OAuth"를 푸는 B2B 도구다. 사용자가 한 명이고 토큰이 이미 맥에 있는 tidy-one에는 맞지 않고, 토큰을 제3자에게 맡기게 만든다.

그래서 **커넥터는 맥의 launchd 아래 도는 작은 폴러 네 개**(노션, 구글, Plaud, `gh` API를 쓰는 GitHub)로 직접 쓴다. Slack은 아래 정책 섹션의 이유로 폴러를 두지 않는다. 맥에서 돌리는 이유는 세 가지다. 인증(`gws` OAuth, Plaud 토큰, `gh` 로그인)이 이미 맥에 있다. 임베딩도 어차피 맥 GPU에서 한다. 인터넷에 노출된 서버에 새로고침 토큰을 두면 피해 범위가 커진다. 맥이 잠든 동안 동기화가 멈추지만 커서 기반 API는 깨어난 뒤 따라잡으므로 개인 색인에는 문제가 없다. 예외는 일주일 넘게 끊긴 Gmail뿐이다. 설계는 **Onyx의 커넥터 코드**(MIT, `ee/` 밖)를 참고한다. 전체 백필(Load), 시간 구간 증분(Poll), 삭제를 걸러 내는 ID 전용 점검(Slim)의 세 단계는 tidy-one에 필요한 구조와 정확히 맞는다 ([Onyx connectors README](https://github.com/onyx-dot-app/onyx/blob/main/backend/onyx/connectors/README.md)). dlt는 쓰지 않는다. 노션 소스가 증분이 아닌 전체 교체(`replace`)이고, 슬랙 커서가 `created_at`만 봐서 편집과 늦은 스레드 답글을 놓친다 ([dlt notion](https://github.com/dlt-hub/verified-sources/blob/master/sources/notion/__init__.py), [dlt slack](https://github.com/dlt-hub/verified-sources/blob/master/sources/slack/__init__.py)).

**노션**은 2026년의 개인 접근 토큰(PAT)이 판을 바꿨다. PAT는 만든 사람의 권한으로 동작하므로 페이지마다 "연결 추가"를 할 필요가 없다. 만료는 7일에서 1년(기본)까지 고를 수 있다 ([PAT guide](https://developers.notion.com/guides/get-started/personal-access-tokens.md), [changelog](https://developers.notion.com/page/changelog.md)). 속도 제한은 연결당 분당 180회(Business·Enterprise는 600회)이고, 워크스페이스 공유 한도가 따로 있다 ([Request limits](https://developers.notion.com/reference/request-limits.md)). 증분은 `POST /v1/search`를 `last_edited_time` 내림차순으로 넘기다 저장해 둔 최고 수위에 닿으면 멈춘다. 삭제는 `in_trash: true` 점검으로 잡는다 ([POST /v1/search](https://developers.notion.com/reference/post-search.md)). API 버전 2026-03-11부터 AI 회의록은 `meeting_notes` 블록이 되어 요약·노트·전사를 각각의 하위 블록 ID로 가져온다 ([Upgrade guide](https://developers.notion.com/guides/get-started/upgrade-guide-2026-03-11)). 웹훅은 내용 없이 "바뀌었다"는 신호만 주고 공개 HTTPS 수신자가 필요하므로 ([webhooks](https://developers.notion.com/reference/webhooks/page-content-updated)), 1인에게는 15~60분 폴링이 더 단순하다.

**구글**은 네 소스 중 증분 기능이 가장 깔끔하다. Drive는 `changes.getStartPageToken` → `changes.list` → `newStartPageToken` 순서로 돈다 ([Drive changes](https://developers.google.com/workspace/drive/api/guides/manage-changes)). Gmail은 저장한 `historyId`부터 `history.list`를 부른다. 이력은 "보통 최소 일주일" 남고, 범위를 벗어나면 404가 와서 전체 동기화를 다시 해야 한다 ([Gmail sync](https://developers.google.com/workspace/gmail/api/guides/sync)). 사용자의 `gws` CLI(Apache-2.0)가 이 메서드를 모두 제공하므로 ([googleworkspace/cli](https://github.com/googleworkspace/cli)) 파이썬 OAuth 클라이언트를 새로 만들 필요가 없다. 주의할 함정이 하나 있다. 외부 사용자 유형에 "테스트" 상태인 OAuth 클라이언트는 **새로고침 토큰이 7일 만에 만료**된다 ([Google OAuth](https://developers.google.com/identity/protocols/oauth2#expiration)). 개인 Gmail 계정용 클라이언트는 "프로덕션"으로 옮겨야 한다. 문서 단위는 Gmail은 인용문을 걷어 낸 스레드 하나, Docs는 Markdown 제목 단위, 슬라이드는 장 단위, 시트는 탭별 행 묶음이다.

**Plaud**는 2026년 5월 12일 개인용 MCP와 CLI(`@plaud-ai/cli`)를 정식 출시했다 ([Plaud changelog](https://docs.plaud.ai/plaud-mcp-cli/changelog.md)). "Plaud Developer Platform" REST API는 파트너용 B2B API라 자기 녹음을 내보내는 용도가 아니다 ([Plaud docs index](https://docs.plaud.ai/llms.txt)). CLI는 `plaud recent --days N`, `plaud transcript`, `plaud summary`를 제공하고, 토큰을 `~/.plaud/tokens.json`에 둔다. 변경 피드나 웹훅은 없다 ([Plaud CLI](https://docs.plaud.ai/plaud-mcp-cli/cli.md)). 그래서 매 실행마다 최근 며칠치 ID를 카탈로그와 비교하고, 전사와 요약이 비동기로 완성·재생성되는 점을 감안해 며칠간은 다시 가져온다. npm 레지스트리의 버전(0.3.x)이 체인지로그의 "v1.0.0"과 맞지 않는 점은 아직 설명되지 않았다 ([npm](https://www.npmjs.com/package/@plaud-ai/cli)). 기존 Plaud→Whisper→Notion 파이프라인과 겹치지 않게 하려면 노션 페이지 속성에 Plaud 파일 ID를 넣고 그 ID로 중복을 제거한다. 오디오는 저장하지 않고, 필요할 때 24시간짜리 URL을 새로 받는다.

**Slack**은 기술적으로는 쉽다. 자기 워크스페이스에 만든 내부 앱은 2025년 5월 속도 제한 강화(분당 1회·15개)의 대상이 아니다. 그래서 Tier 3와 요청당 최대 1,000개를 유지한다 ([Slack changelog](https://docs.slack.dev/changelog/2025/05/29/rate-limit-changes-for-non-marketplace-apps)). 문제는 약관이다. 이 부분은 정책 섹션에서 다루며, 결론부터 말하면 Slack은 색인하지 않는다.

## 공통 스키마는 Onyx의 Document를 본떠 테이블 아홉 개로 충분하다

모든 종류를 한 카탈로그에 넣으려면 "문서"의 정의를 넓혀야 한다. 출발점으로는 Onyx의 정규화된 `Document`가 좋다. id, source, 링크가 붙은 sections(텍스트·이미지·표), title, metadata, 갱신 시각, 소유자, 그리고 ACL인 `external_access`를 갖는다 ([Onyx models.py](https://github.com/onyx-dot-app/onyx/blob/main/backend/onyx/connectors/models.py)). 여기에 사진·영상의 시간·장소·프레임과 개인정보 등급을 더한다. 핵심 원칙은 네 가지다. 첫째, `doc_id`는 출처별 접두어로 전역 유일하게 만든다. 둘째, 모든 텍스트는 `chunks`에 "어느 필드에서 왔는지(본문·OCR·전사·캡션·라벨)"와 함께 넣는다. 셋째, 벡터는 모델별로 다른 테이블에 넣고 절대 섞지 않는다. 넷째, 삭제는 행을 지우지 않고 묘비(`deleted_at`)로 표시한다.

```sql
-- 출처와 커서
sources(source_id, kind,            -- file|photos|notion|gdrive|gmail|plaud|github|slack_ptr
        account, workspace, device_id, default_visibility, enabled)
cursors(source_id, cursor_kind,     -- fsevents_id|usn|hexdigest|last_edited_time|startPageToken|historyId|created_at
        value, updated_at)

-- 문서: doc_id = 'file:<device>:<path-hash>' | 'photos:<uuid>' | 'notion:<ws>:<page>' | 'gmail:<acct>:<thread>' | 'plaud:<acct>:<file>'
documents(doc_id, source_id, native_id, modality,   -- text|image|video|audio|message
          title, uri, mime, author, participants,
          created_at, updated_at, taken_at, duration_s,
          geo_cell, place_ko, place_en, persons,     -- persons는 옵트인, 이름만
          labels, content_hash, phash, parent_id,
          visibility,                                -- private|shared|workspace|company-restricted
          sensitivity,                               -- none|meeting|screen|face|id 등 비트 플래그
          deleted_at, extra_json)

-- 텍스트 청크와 두 FTS
chunks(chunk_id, doc_id, ordinal, field,             -- body|ocr|asr|caption|summary|labels|meta
       page, t_start, t_end, text, text_morph, chunk_hash, token_count)
chunks_fts      USING fts5(text_morph, title)        -- Kiwi 형태소를 공백으로 이은 열, unicode61
chunks_trigram  USING fts5(text, tokenize='trigram') -- OCR·파일명·식별자 보조

-- 두 벡터 공간 (sqlite-vec vec0), 모델 등록부
vec_text   USING vec0(chunk_id, embedding int8[1024], modality TEXT PARTITION KEY)
vec_visual USING vec0(frame_id, doc_id, t_sec, embedding int8[768])
models(model_id, space, dim, quant, active)
```

sqlite-vec은 float·int8·binary 벡터와 메타데이터·파티션 키 열을 지원한다 ([sqlite-vec](https://github.com/asg017/sqlite-vec)). 모델을 바꿀 때는 새 `model_id`로 테이블을 따로 만들어 다시 임베딩한 뒤 전환한다. 다시 임베딩하는 데 B/16 기준 3만 장이면 M2에서 수십 분이다(추정). `chunk_hash`에는 정규화한 텍스트, 모델 ID, 접두어를 포함시켜, 바뀐 청크만 다시 임베딩되게 한다. 이 방식은 이전 조사의 설계를 그대로 이어받은 것이다. 구조화 필드(`taken_at`, `geo_cell`, `place_ko`, `persons`, `modality`)는 SQL 필터로만 쓰고, 텍스트로도 한 번 더 `field='meta'` 청크에 넣는다. 그러면 "제주"라는 단어가 장소 필터를 거치지 않은 질의에서도 잡힌다. Apple 라벨이 영어로 저장되는지 한국어로 저장되는지는 확인되지 않았다. 영어라면 Kiwi 키워드는 놓치지만 다국어 텍스트 벡터가 언어를 넘어 맞춘다. 라벨 어휘는 유한하니 한 번 만든 한영 대응표로 `labels` 청크에 한국어를 함께 적는 방법도 있다(제안).

검색 도구는 이 스키마 위에서 하나로 충분하다. `search(query, query_en?, kind?, source?, date_from?, date_to?, place?, person?, k)`는 다섯 단계로 동작한다. ① SQL 필터를 적용한다. ② Kiwi로 분석한 질의로 `chunks_fts`를 찾고, 질의가 짧거나 식별자 모양이면 `chunks_trigram`도 찾는다. ③ 한국어 텍스트 벡터로 `vec_text`를 kNN 검색한다. ④ `kind`가 비었거나 사진·영상이면 SigLIP2 텍스트 벡터로 `vec_visual`을 kNN 검색한다. ⑤ 세 결과를 RRF로 합치고, `doc_id`와 중복 해시로 묶는다. 결과는 원문 대신 발췌, 점수, 페이지나 타임스탬프, 출처, 열기용 URI를 페이지 단위로 돌려준다. 원문은 `fetch(doc_id, offset, length)`로 가져와 Claude Code의 25k 토큰과 Codex의 60초 제한 안에 머문다 ([Claude Code MCP](https://code.claude.com/docs/en/mcp), [Codex](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)). 입력 스키마가 16KiB를 넘는 도구는 claude.ai가 조용히 누락시킨다는 보고가 있으므로 ([claudeissues #77296](https://claudeissues.com/issue/77296-bug-claude-ai-connector-ingestion-silently-drops-any-tool-with-inputschema-16-38)) 인자는 위 수준으로 작게 유지한다.

여기서 원칙 하나가 자연스럽게 따라 나온다. **서버는 SaaS 자격 증명을 갖지 않는다.** 그러니 노션·구글 문서의 `fetch`는 저장된 청크와 원본 URL만 돌려준다. 최신 원문이 필요하면 호출한 클라이언트가 자신의 1차 커넥터(Notion MCP, Google Drive 커넥터)로 그 URL을 연다. 기기 파일과 영상 전사 원문은 기기가 깨어 있을 때 tailnet으로 가져오고, 잠들어 있으면 "오프라인, 마지막 접속 T"와 발췌를 돌려준다는 이전 설계를 그대로 쓴다.

## 4GB 서버는 두 텍스트 인코더와 카탈로그만 상주시킨다

claude.ai는 Anthropic 클라우드에서 공개 엔드포인트로만 들어온다 ([Claude Help Center](https://support.claude.com/en/articles/11175166-getting-started-with-custom-connectors-using-remote-mcp)). 그래서 질의 임베딩은 맥이 잠들어 있어도 서버에서 계산돼야 한다. 다행히 듀얼 인코더 구조 덕분에 서버가 필요한 것은 **텍스트 쪽 절반**뿐이다. 이미지 타워는 맥에만 두고, 서버는 SigLIP2의 텍스트 ONNX와 한국어 텍스트 인코더만 띄운다. 아래 예산은 공개 수치에서 산술로 추정한 것이며, 실측 전에는 설계 가정일 뿐이다.

| 구성 요소 | 상주 메모리 (추정) | 근거 |
|---|---|---|
| OS, Tailscale, mcp-auth-proxy, 허브 MCP 프로세스 | 0.4~0.6GB | 추정, 근거 없음 |
| 한국어 텍스트 인코더 (bge-m3 또는 KURE-v1) int8 ONNX | 약 0.6GB (fp16이면 약 1.1GB) | Ollama bge-m3 F16 적재 약 1.06GB ([morphllm](https://www.morphllm.com/ollama-embedding-models))에서 산술 |
| SigLIP2-B/16 텍스트 타워 int8 / fp16 | 약 0.3GB / 약 0.56GB | fp32 ONNX 1,164MB ([Immich HF](https://huggingface.co/immich-app/ViT-B-16-SigLIP2__webli/tree/main))에서 산술 |
| Basic Memory의 MiniLM (통합 전까지) | 약 0.67GB | [Basic Memory benchmark](https://github.com/basicmachines-co/basic-memory/blob/main/docs/multilingual-embedding-benchmark.md) |
| SQLite 카탈로그 캐시 | 0.2~0.4GB | 텍스트 청크 10만 개 × 1024차원 int8 ≈ 100MB, 사진 3만 + 프레임 6만 × 768차원 int8 ≈ 70MB, FTS 별도 |
| **합계** | **약 2.2~2.9GB** (Basic Memory 통합 후 약 1.5~2.2GB) | 4GB에서 1GB 이상 여유 |

Immich 표에 나오는 SigLIP2-B/16의 "3,038MiB"는 fp32 전체 프로세스의 최대 RSS다 ([Immich docs](https://docs.immich.app/features/searching)). 텍스트 타워만 양자화해 띄우는 경우를 과대평가한 값이다. 지연도 대화형으로 충분하다. 20토큰 안팎 질의 하나를 568M 모델에 넣는 데 1 vCPU에서 0.2~0.5초, SigLIP2-B/16은 Immich 표에서 데스크톱 CPU 기준 5.8ms(텍스트·이미지 중 어느 쪽 수치인지는 명시되지 않음)이므로 2 vCPU에서 텍스트 타워는 수십 ms로 추정된다. 둘 다 실측은 없다. 이는 claude.ai의 호출당 240초나 Codex의 60초와 비교하면 여유가 크다 ([Claude docs: Build](https://claude.com/docs/connectors/building)). 이전 계획에서 두 모델이 2GB를 두고 다투던 문제는 4GB에서 풀린다. Basic Memory의 노트 검색까지 허브의 같은 한국어 모델로 합치면 상주 모델이 셋에서 둘로 줄어 여유가 더 커진다.

**서버에 올리지 말아야 할 것도 분명하다.** 첫째, 재순위기다. 0.6B 교차 인코더가 후보 20개를 읽으면 CPU에서 수십 초가 걸릴 것으로 추정된다. 둘째, Qwen3-VL-Embedding-2B다. 셋째, SigLIP2 L·SO400M의 fp32 텍스트 타워(2.3~2.9GB)다. 넷째, NLLB-CLIP이다. 1.7GB인 데다 비상업 라이선스다. OCR, ASR, 캡션, 이미지 임베딩은 말할 것도 없다. SigLIP2 L이나 SO400M으로 올리고 싶다면 int8 텍스트 타워의 RSS와 정확도 손실을 먼저 재야 한다. 둘 다 아직 측정한 출처가 없다.

규모가 커질 때를 대비한 장치도 둔다. 이전 조사에서 5만 청크 정도는 sqlite-vec의 전수 KNN으로 충분하다고 봤다. 텍스트 청크가 수십만 개로 늘면 `modality` 파티션 키로 범위를 좁힌다. 그래도 느리면 binary 벡터로 거칠게 걸러 낸 뒤 int8로 다시 점수를 매기는 2단계 검색으로 바꾼다(sqlite-vec은 bit 벡터를 지원한다, [sqlite-vec](https://github.com/asg017/sqlite-vec)). 서버 RAM이 결국 모자라면 물러설 길이 두 개 있다. 하나는 SigLIP2 텍스트 타워를 내리는 것이다. 그래도 사진·영상은 OCR·라벨·캡션·장소 텍스트로 계속 검색되고, 시각 검색만 tailnet으로 맥에 직접 붙는 로컬 클라이언트(Claude Code)에 남는다. 다른 하나는 도구 설명에 영어 의역(`query_en`)을 함께 보내라고 요구하는 것이다. 호출자가 LLM이라 가능하며, 영어 라벨과의 키워드 매칭이 좋아진다. 다만 Aside나 단순 클라이언트가 이를 따를지는 보장되지 않으므로 보조 수단으로만 쓴다.

## 가장 큰 위험은 Slack 약관, 얼굴, 회의 원문이다

4GB로 RAM 제약이 풀리면 설계를 묶는 조건은 계약과 법으로 넘어간다. 가장 분명한 선은 **Slack API 약관(2025-05-29 개정)**이다. 약관은 API 데이터로 LLM을 학습하는 것을 금지한다. 메시지·파일 데이터의 대량 내보내기는 "추가 계약으로 명시적으로 허용된 경우"에만 허용한다. Data Access API에 대해서는 "영구 사본, 아카이브, 색인, 장기 데이터 저장소"를 만들지 못하게 한다. 내부 앱에 대한 예외 조항은 찾지 못했다 ([Slack API ToS](https://slack.com/policy-archives/terms-of-service-api/2025-05-29)). 한 로펌은 이를 아카이브와 색인을 폭넓게 금지하는 것으로 읽고, Slack 아카이브 위에 내부 LLM을 만든 고객은 설계를 바꿔야 한다고 본다 ([Hunton](https://www.hunton.com/privacy-and-cybersecurity-law-blog/salesforce-locks-down-slack-data-time-to-review-your-slack-api-terms)). Slack이 AI 에이전트에게 열어 둔 길은 그 자리에서 조회하는 방식이다. Slack MCP 서버(`mcp.slack.com/mcp`)는 관리자 승인과 감사 로그를 거치고 ([Slack MCP](https://docs.slack.dev/ai/slack-mcp-server/)), Real-time Search API는 요청당 20개, 사용자당 분당 10회로 동작한다 ([assistant.search.context](https://docs.slack.dev/reference/methods/assistant.search.context)). 그래서 Slack은 tidy-one이 색인하지 않는다. claude.ai와 Claude Code에 이미 있는 Slack 커넥터가 tidy-one 검색과 나란히 호출되도록 두는 **클라이언트 쪽 연합**이 가장 안전하다. 서버 안에서 Slack을 대신 조회하려면 Slack 사용자 토큰을 서버에 둬야 하는데, 이는 "서버는 SaaS 자격 증명을 갖지 않는다"는 원칙과 부딪친다. 저장이 꼭 필요하다면 본인 메시지와 저장한 항목의 링크만 두고, 워크스페이스 소유자의 서면 승인을 남긴다.

나머지 회사 소스도 관리자의 눈에 보인다. 노션 PAT는 관리자가 목록을 보고 철회할 수 있고, Business 플랜의 기본값은 소유자만 PAT를 만들 수 있게 한다 ([PAT guide](https://developers.notion.com/guides/get-started/personal-access-tokens.md)). 구글 관리자는 서비스 제한으로 새로고침 토큰을 무효화할 수 있다(`admin_policy_enforced`, [Google OAuth](https://developers.google.com/identity/protocols/oauth2#expiration)). 더 근본적인 문제는 소재지다. company의 Drive·Gmail 사본이 개인이 운영하는 Vultr 서버에 쌓이는 것은 회사의 데이터 소유·보관 정책 문제다. 동료의 DM과 스레드는 제3자의 개인정보다. 이를 개인 서버에 보관할 때의 한국 개인정보보호법 요건은 이번 조사에서 다루지 않았다. 사용자가 회사 소유자이더라도 "무엇을, 어디에, 얼마나 보관하고, 퇴사·종료 때 어떻게 지우는가"를 한 문단짜리 데이터 처리 메모로 남겨 두는 편이 낫다. Plaud의 원격 MCP는 데이터가 미국 서버를 "전송 중에만" 거친다고 밝히므로 ([Plaud MCP](https://docs.plaud.ai/plaud-mcp-cli/mcp.md)), 수집에는 맥의 CLI를 쓴다.

개인 자료 쪽의 가장 민감한 파생물은 얼굴이다. 한국 개인정보보호법 시행령 제18조 3호는 개인을 고유하게 식별할 목적으로 신체적·생리적·행동적 특징을 기술적으로 처리한 정보를 **민감정보**로 규정한다 ([Securiti](https://securiti.ai/south-korea-personal-information-protection-act/), [Hunton](https://www.hunton.com/privacy-and-cybersecurity-law-blog/korea-announces-regulations-to-personal-information-protection-act)). Immich가 쓰는 InsightFace 사전 학습 모델은 비상업 연구용이다 ([PyPI insightface](https://pypi.org/project/insightface/)). 그러니 얼굴 벡터는 계산하지 않는다. macOS 27의 osxphotos는 여권·신분증에서 읽은 이름(`id_document_names`)까지 노출하는데 ([searchinfo.py](https://github.com/RhetTbull/osxphotos/blob/main/osxphotos/searchinfo.py)), 이 필드는 어떤 경우에도 서버로 보내지 않는다. 회의 녹음에는 다른 사람의 목소리와 이름이 들어 있다. 화자 분리는 신원이 아니라 화자 라벨만 준다 ([whisperX](https://github.com/m-bain/whisperX)). 화면 녹화에는 비밀번호, 대화, 고객 데이터가 찍힐 수 있다. Underpin 운영 화면이 그런 예다.

모델 라이선스도 같은 선 위에 있다. NLLB-CLIP, jina-clip-v2, jina 재순위기는 CC-BY-NC다. MobileCLIP2와 FastVLM은 Apple 연구용 라이선스다 ([ml-mobileclip](https://github.com/apple-aiml-research/ml-mobileclip), [ml-fastvlm](https://github.com/apple-aiml-research/ml-fastvlm)). ImageBind는 CC BY-NC-SA다. Surya의 가중치는 연구·개인·매출 500만 달러 미만 스타트업에만 무료다 ([Surya](https://github.com/datalab-to/surya)). 회사 업무에도 쓰는 색인이라면 Apache-2.0·MIT 모델만 남긴다. 이 보고서가 고른 SigLIP2, Qwen3-ASR, Qwen3-VL, bge-m3·KURE-v1, PP-OCRv5는 모두 이 조건을 통과한다.

| 회사 Slack | API 약관이 대량 내보내기·LLM 학습·Data Access API 색인을 금지 | 색인하지 않음. 클라이언트의 Slack 커넥터로 연합. 저장은 본인 저장 항목 링크만, 소유자 서면 승인 후 |
| 팀 Notion | PAT가 관리자에게 보이고 철회 가능, Business 기본은 소유자만 생성 | 공개·승인 후 PAT 또는 관리자가 승인한 내부 통합. `visibility=company-restricted` |
| 회사 Drive·Gmail | 관리자 차단 가능, 개인 서버에 회사 사본 | 데이터 처리 메모 작성 뒤에만 색인. tailnet의 로컬 클라이언트에만 노출 |
| 개인 Gmail·Notion·Drive·Plaud | 메일은 신뢰할 수 없는 입력(프롬프트 인젝션) | 색인하되 결과에 출처를 붙이고 도구는 읽기 전용 |
| 사진 얼굴·신분증 | 개인정보보호법상 민감정보, InsightFace 비상업 | 얼굴 벡터 없음, 인물 이름만 옵트인, `id_document_*` 전송 금지 |
| GPS | iPhone 영상·사진의 정밀 위치 | 100m~1km 격자와 지명만 중앙에 |
| 회의 녹음·화면 녹화 | 타인 목소리, 비밀번호, 고객 데이터 | 전사 원문·OCR은 기기에. 중앙에는 요약과 벡터만, `sensitivity` 표시 |
| 썸네일 | 가장 많이 드러나는 파생물 | 기본 끔, 필요하면 맥에서 온디맨드 |

기술적 통제는 이 표를 강제하는 장치다. MCP 도구는 `visibility`와 `sensitivity`로 거른다. 공개 정문(claude.ai 웹·iOS)으로 온 요청에는 `company-restricted`와 민감 표시 결과를 숨기고, tailnet으로 붙은 로컬 Claude Code에만 보여 준다. 출처별 일괄 삭제(`DELETE … WHERE source_id = …`)를 처음부터 넣어 둔다. 서버 디스크와 SQLite 백업은 암호화한다. 노션 PAT 같은 비밀은 macOS 키체인이나 1Password CLI에 두고, `gws`와 `plaud`의 토큰은 각 CLI가 관리하는 곳에 그대로 둔다. `gws auth export`는 복호화된 자격 증명을 표준 출력으로 내보내므로 ([googleworkspace/cli](https://github.com/googleworkspace/cli)) 그 출력이 저장소, `~/claude-memory`, 서버로 흘러가지 않게 한다. 서버에는 카탈로그 쓰기 범위로 제한된 수집 키 하나만 둔다.

마지막으로, 메일과 메신저를 색인에 넣는 순간 이전 보고서가 경고한 "개인 데이터 접근, 신뢰할 수 없는 입력, 외부 통신"의 세 조건 중 두 번째가 크게 늘어난다. 메일 본문은 프롬프트 인젝션의 교과서적인 통로다. 그러니 읽기 전용 도구, 경로 허용 목록, 결과의 출처 표시, 클라이언트의 도구별 승인 기능을 끄지 않는 원칙은 이 확장에서 더 중요해진다.

## 실측 관문에서 회사 데이터까지 일곱 단계로 쌓는다

순서의 원칙은 세 가지다. 첫째, 모든 종류가 결국 텍스트가 되므로 텍스트 경로를 먼저 완성한다. 둘째, 각 종류에서 이미 남이 계산해 둔 것(Apple의 사진 분석, Plaud 전사, 구글의 Markdown 내보내기)을 먼저 받는다. 셋째, 정책이 막는 것은 맨 뒤로 미룬다. 이전 계획의 0~2단계(정문 점검, 사설망, 한국어 품질 검증)는 이 확장의 전제다.

| 단계 | 할 일 | 차용 부품 | 완료 기준 |
|---|---|---|---|
| E0. 실측 관문 | 서버에 bge-m3(또는 KURE-v1) int8 ONNX와 SigLIP2-B/16 텍스트 타워를 함께 띄워 RSS와 p95 지연 측정. 맥에서 사진 500장 SigLIP2-B·SO400M 처리량, 5분 한국어 회의로 Qwen3-ASR-1.7B 8비트 대 mlx-whisper turbo, 프레임 20장 Qwen3-VL-2B·4B 캡션 측정. `osxphotos query --json`으로 보관함 규모, iCloud 최적화 비율, Apple OCR·캡션 채움률, 라벨 언어 확인 | onnxruntime, mlx-audio, mlx-vlm, osxphotos | 상주 합계 2.5GB 이하, 질의 p95 1초 이하(제안 기준). 넘으면 SigLIP2 텍스트 타워를 빼는 대안으로 전환 |
| E1. 공통 스키마 + 문서 | 테이블 9개(일반 5 + 가상 4), Kiwi + trigram FTS, `search`·`fetch`에 `kind`·날짜·장소 필터 추가. 이전 계획 3단계의 맥 문서 에이전트를 이 스키마로 구현. Basic Memory 노트 검색을 같은 한국어 모델로 통합 | sqlite-vec, Kiwi, markitdown, docling(ocrmac accurate), kordoc | 맥 문서·노트를 한 도구로 검색. 서버 상주 모델이 2개로 줄어듦 |

E0을 맨 앞에 둔 이유는 이 설계의 유일한 하드웨어 가정이 4GB 서버에 두 텍스트 인코더가 함께 들어간다는 추정이기 때문이다. 이 가정이 틀리면 E3b의 위치가 바뀐다. E2를 사진보다 앞에 둔 이유는 클라우드 텍스트가 새 모델 없이 E1의 텍스트 경로를 그대로 쓰기 때문이다. 업무 질의("그 회의에서 뭐라고 했지")에서 가치가 가장 크면서 맥의 연산은 거의 쓰지 않는다. 사진을 3a·3b·3c로 쪼갠 것은 3a만으로도 Apple이 이미 계산한 OCR과 라벨 덕분에 상당한 검색이 되기 때문이다. 캡션 모델의 40~80시간 비용을 들이기 전에 실제로 무엇이 부족한지 확인할 수 있다. 영상에서 전사를 키프레임보다 앞에 둔 것은 회의·강의 영상의 정보가 대부분 음성에 있고, 전사 결과가 기존 Plaud 파이프라인의 ASR 교체 판단에도 쓰이기 때문이다. 회사 소스를 E5로 미룬 것은 기술적으로는 E2와 같은 작업이지만, 막는 것이 코드가 아니라 승인과 약관이기 때문이다.

> **참고 영상**: 영상 없음. 이 단계 계획은 사용자 환경에 맞춘 조합이라 그대로 대응하는 공식 데모가 없다. 각 단계의 개념 영상은 앞 섹션에 있다.

## 결론

이번 확장 조사로 tidy-one의 정체가 바뀌었다. 처음에는 "파일을 찾는 색인"이었지만, 네 종류를 모두 다루고 나면 **다른 시스템이 이미 계산한 의미를 한국어 텍스트로 번역해 모으는 층**이 된다. Apple은 사진의 OCR·라벨·캡션을, Plaud는 전사와 요약을, 구글은 Markdown 내보내기를, Slack과 노션은 실시간 검색을 이미 제공한다. tidy-one이 직접 모델을 돌려야 하는 곳은 그 공백, 즉 사진 보관함 밖의 이미지, 영상 음성, 그리고 픽셀 자체뿐이다. 그래서 검색 품질의 지렛대는 여전히 한국어 텍스트 임베딩과 Kiwi 형태소 열 하나에 몰려 있다. 시각 벡터는 "어떻게 보이는가"를 묻는 질의를 위한 두 번째 경로에 그친다. 이 점이 Immich나 VideoRAG처럼 시각 모델을 중심에 두는 제품과 갈리는 지점이다. 또 하나의 변화는 제약의 종류다. 2GB에서는 RAM이 설계를 묶었지만, 4GB에서는 Slack 약관, 개인정보보호법상 민감정보, 비상업 모델 라이선스가 경계선이 된다. 그 결과 "색인하지 않고 연합한다"가 정식 설계 선택지로 올라왔다.

남은 불확실성은 측정과 확인으로만 풀린다. 서버에 두 인코더를 함께 띄웠을 때의 실제 RSS와 지연, SigLIP2 텍스트 타워의 int8 정확도 손실, Apple 라벨·캡션의 저장 언어, 대화체 한국어 회의에서 Qwen3-ASR의 실제 오류율, Qwen3-VL의 한국어 캡션 품질이 측정 대상이다. 조직 쪽에서는 company의 Slack 앱 승인 설정, Google Workspace API 통제, 노션 플랜과 PAT 정책을 확인해야 한다. 앞의 것들은 E0에서 하루 안에 측정할 수 있고, 뒤의 것들은 회사 소스를 다루는 E5 전에 서면으로 정리하면 된다.
