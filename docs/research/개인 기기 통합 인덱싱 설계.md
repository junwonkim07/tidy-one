# 원본은 기기에 두고, 색인만 서울로 모아라

**권장 설계는 "하이브리드 연합형"이다.** 마크다운 메모리 저장소는 지금처럼 git으로 모든 기기에 동기화하고, VPS가 GitHub에서 직접 받아 상시 색인한다. 그 밖의 파일은 맥·윈도우에 둔 경량 에이전트가 메타데이터, 짧은 발췌, 기기에서 계산한 임베딩만 VPS의 SQLite(FTS5 + sqlite-vec) 카탈로그로 밀어 넣는다. 원본은 기기에 남겨 두고 Tailscale로 필요할 때만 가져온다. 모든 AI 클라이언트는 이미 구성 중인 VPS의 공개 OAuth MCP 엔드포인트(Basic Memory + mcp-auth-proxy) 하나로 들어온다. 이렇게 나누는 근거는 세 가지다. 첫째, claude.ai(웹·iOS)는 사용자 기기가 아니라 Anthropic 클라우드에서 서버에 접속하므로 공개 HTTPS 엔드포인트가 반드시 있어야 한다. 둘째, 1 vCPU/2GB VPS에는 Khoj(4~8GB), Onyx(10GB), Immich(6GB)처럼 "전부 서버로 복사해 서버에서 임베딩하는" 제품을 올릴 수 없다. 셋째, 조사한 약 35개 오픈소스 중에 세 OS용 기기 에이전트, 2GB에 맞는 중앙 색인, claude.ai용 원격 OAuth MCP, 쓸 만한 한국어 임베딩을 모두 갖춘 제품이 없다. 그래서 Basic Memory, qmd의 검색 설계, sqlite-vec, Everything·Spotlight, Tailscale, mcp-auth-proxy를 조립하고, 직접 만드는 부분은 기기 에이전트와 허브 MCP라는 얇은 층으로 한정한다. 검색 품질을 가장 크게 올리는 방법은 제품 교체가 아니라 모델 교체다. 지금 쓰는 multilingual MiniLM은 한국어 특화 bge-m3 계열(KURE, snowflake-ko)에 크게 뒤진다. SQLite 기본 토크나이저는 한국어 조사를 떼지 못하므로 Kiwi 형태소 열을 따로 둬야 한다. 아이폰은 백그라운드 색인을 돌릴 수 없으니 색인 대상에서 빼고, claude.ai iOS 앱으로 조회하면서 단축어나 Working Copy로 가끔 자료를 올리는 클라이언트로 쓴다. 보안의 핵심은 "모든 기기를 읽을 수 있는 허브는 그 자체로 유출 통로"라는 점이다. 이는 읽기 전용 도구, 경로 허용 목록, `tag:hub`만 기기에 닿게 하는 Tailscale ACL, 토큰 패스스루 금지로 막는다.

## 35개 오픈소스 중 그대로 설치할 완성품은 없지만, 조립할 부품은 충분하다

조사 대상은 개인의 파일·노트·기억을 여러 기기에서 색인해 AI에 넘겨주는 약 35개 프로젝트였다. 판정 기준은 이 사용자의 네 조건이다: 맥·윈도우·iOS용 기기 에이전트, 2GB VPS에 맞는 단일 중앙 색인, claude.ai 웹·모바일이 쓸 수 있는 OAuth 원격 MCP 서버, 기본 한국어 품질. 네 조건을 모두 만족하는 프로젝트는 하나도 없었고, 각 후보는 한두 개만 채운다.

**Khoj**는 "기기 에이전트 → 중앙 서버" 구조가 가장 완성돼 있다. 데스크톱, Obsidian, Emacs, Android 클라이언트가 파일을 서버로 밀어 넣는다. 다만 데스크톱 앱은 10분마다 mtime을 비교해 바뀐 파일의 전체 내용을 `/api/content`로 올리는 단순 폴링 방식이다 ([khoj main.js](https://github.com/khoj-ai/khoj/blob/HEAD/src/interface/desktop/main.js)). 결정적으로 Khoj는 MCP *클라이언트*일 뿐 서버 엔드포인트가 없고, 2026년 7월에도 이를 요청하는 이슈가 열려 있다 ([#1364](https://github.com/khoj-ai/khoj/issues/1364)). 호스팅 가이드는 메모리를 최소 4GB, 권장 8GB로 제시한다 ([RamNode](https://ramnode.com/guides/khoj)). 마지막 릴리스는 2026년 3월 베타이고, README는 회사의 새 제품(Pipali, Open Paper)을 앞세우고 있다 ([README](https://github.com/khoj-ai/khoj)).

**Onyx**는 Claude Code·Codex용 MCP 서버를 갖췄지만, 색인이 가능한 에디션은 최소 4 vCPU/10GB가 필요하다. 2GB로 도는 "Lite"는 문서를 색인하지 못한다 ([Onyx docs](https://docs.onyx.app/deployment/getting_started/resourcing)).

**Nextcloud + nextcloud-mcp-server**는 세 OS 모두에 공식 동기화 클라이언트가 있고, 110개가 넘는 도구를 가진 OAuth MCP를 제공한다. 그러나 의미 검색은 Qdrant + Ollama가 필요한 실험 기능이다 ([repo](https://github.com/cbcoutinho/nextcloud-mcp-server)). Nextcloud 자체의 Context Chat은 CPU 기준 12GB 이상을 요구한다 ([Nextcloud docs](https://docs.nextcloud.com/server/latest/admin_manual/ai/app_context_chat.html)).

**Screenpipe**는 기기별 화면·음성 기록과 MCP 서버를 제공하지만, 기록은 각 기기에 머물고 기기 간 동기화는 유료 Business 플랜에 묶여 있다. 라이선스도 상용 소스 공개 라이선스로 바뀌어 개인 비상업 용도만 무료다 ([LICENSE.md](https://github.com/screenpipe/screenpipe/blob/main/LICENSE.md)). 회사(immensus) 업무에 쓰면 상용 사용으로 해석될 수 있다.

**Supermemory**는 자체 호스팅 모드에서 MCP 서버와 커넥터가 빠지고 서버 바이너리가 비공개 코드라 제외했다 ([self-host docs](https://supermemory.ai/docs/self-hosting/overview)).

프로젝트가 중단될 위험도 크다. mem0는 2026년 7월 29일 OpenMemory MCP를 모노레포에서 제거했고 ([commits](https://github.com/mem0ai/mem0/commits/main/openmemory)), Reor와 obsidian-mcp-tools는 보관(archived) 상태다.

가까운 미래의 후보는 **Spacedrive v2**다. 파일은 제자리에 두고 "내용 인식 색인"만 어디서든 검색할 수 있게 하는 가상 분산 파일시스템이다. Iroh·QUIC 기반 종단 간 암호화 P2P, BLAKE3 콘텐츠 식별, 원격 범위 읽기(range read), MCP 서버를 갖췄고 라이선스는 Apache-2.0이다. 하지만 v2 베타는 2026년 11월 1일에야 나오고, 나이틀리는 macOS ARM64와 Linux x86-64만 지원하며 스키마가 마이그레이션 없이 바뀔 수 있다 ([Spacedrive README](https://github.com/spacedriveapp/spacedrive)). 이 보고서의 연합형 설계는 Spacedrive v2가 약속하는 구조를 지금 쓸 수 있는 부품으로 먼저 만드는 셈이다. 베타가 윈도우와 원격 MCP를 지원하면 직접 만든 기기 에이전트를 Spacedrive로 바꿀 수 있다.

## 중앙 집중은 2GB를 넘고, P2P는 아이폰과 claude.ai를 놓친다

세 가지 아키텍처 계열을 가르는 기준은 원본 사본이 어디에 있고 임베딩을 어디서 계산하느냐다.

**중앙 집중 푸시**는 실제로 출시된 개인 AI 검색 제품의 기본 구조다. Khoj, Open WebUI + oikb(SHA-256 증분 비교와 `watch` 모드), Basic Memory Cloud(rclone bisync로 동기화한 뒤 클라우드에서 색인) 모두 기기가 전체 내용을 서버로 보내고 서버가 파싱·임베딩한다 ([oikb](https://github.com/open-webui/oikb), [Basic Memory cloud sync](https://docs.basicmemory.com/cloud/cloud-sync)). 노트북이 잠들어도 서버에 사본이 있으니 검색과 원문 가져오기가 모두 된다는 것이 가장 큰 장점이다.

대가는 세 가지다. 첫째는 서버 메모리다. Khoj는 4GB 이상, Immich는 6GB 이상(ML을 끄면 4GB)이 필요하다 ([Immich requirements](https://docs.immich.app/install/requirements)). 둘째는 단순한 충돌 처리다. Basic Memory Cloud는 최신 파일이 이기는 `conflict_resolve=newer`에 `max_delete=25` 안전장치를 둘 뿐이다 ([cloud sync](https://docs.basicmemory.com/cloud/cloud-sync)). 셋째, 모든 파일의 평문 사본이 VPS에 쌓이므로 노출 범위가 가장 넓다. 1 vCPU에서 대량 임베딩을 돌리는 비용도 무겁다. 연산량으로 추정하면 568M 파라미터 모델은 512토큰 청크 하나에 4~12초가 걸리고, 2만 청크면 하루가 넘는다(추정이며 실측 아님).

**P2P 동기화 + 기기별 색인**은 사용자가 이미 마크다운에 쓰고 있는 방식이다. Syncthing은 파일시스템 감시자(변경을 10초 단위로 묶음)와 시간당 전체 스캔을 함께 쓰고, 충돌이 나면 한쪽을 `.sync-conflict-<날짜>` 파일로 남긴다 ([Syncthing docs](https://docs.syncthing.net/users/syncing.html)). 각 기기가 자기 사본을 검색하므로 완전히 오프라인이어도 동작하고, 프라이버시도 가장 좋다.

하지만 이 방식은 세 가지 이유로 "모든 파일"까지 넓히기 어렵다. 아이폰은 백그라운드 색인기를 돌릴 수 없고, iOS용 Syncthing 클라이언트조차 하루 1~2시간만 동기화된다 ([Möbius Sync FAQ](https://mobiussync.com/faq/)). 모든 기기가 임베딩 모델을 각각 띄워야 하는데, multilingual MiniLM만 해도 RSS가 약 0.7GB다 ([Basic Memory benchmark](https://github.com/basicmachines-co/basic-memory/blob/main/docs/multilingual-embedding-benchmark.md)). 무엇보다 claude.ai를 쓰려면 어차피 공개 허브가 필요하다. SQLite 색인 파일 자체를 동기화하지 말고 기기마다 다시 만들어야 한다는 점은 Smart Connections 사례에서도 확인된다 ([PromptQuorum](https://www.promptquorum.com/power-local-llm/local-llm-with-obsidian-2026)).

**연합형(메타데이터·임베딩만 중앙화)**은 원본을 기기에 둔다. 허브는 카탈로그(기기, 경로, 크기, mtime, 해시, 발췌, 임베딩)만 갖고, 내용은 필요할 때 사설망으로 가져온다. 2026년 10월 현재 이를 완제품으로 제공하는 오픈소스는 없고 부품만 있다. MCP 집약기(MetaMCP, mcp-proxy, Docker MCP Gateway), 메시 파일 접근(Taildrive), 베타 직전의 Spacedrive v2가 그것이다. Tailscale Aperture는 사설망 안의 MCP들을 묶어 주는 상용 집약기로 2026년 8월 정식 출시됐지만, tailnet 클라이언트 전용이라 claude.ai는 직접 쓸 수 없다 ([Tailscale Aperture docs](https://tailscale.com/docs/aperture/mcp-server), [Aperture GA](https://tailscale.com/blog/aperture-ga)).

카탈로그 자체는 작다. 산술 추정으로 10만 파일의 메타데이터(파일당 약 1KB)는 약 100MB이고, 384차원 float32 벡터는 개당 약 1.5KB다. 약점은 잠든 기기의 원문을 가져올 수 없다는 점이다. Tailscale은 꺼진 기기를 스스로 깨우지 못하며, WoL을 하려면 같은 LAN에 항상 켜진 보조 장치가 있어야 한다 ([Tailscale blog](https://tailscale.com/blog/wake-on-lan-tailscale-upsnap)). 애플 실리콘 맥은 WoL 패킷을 받아도 30~60초 동안 다크웨이크(화면이 꺼진 채 잠깐 깨는 상태)만 한다는 보고가 있다 ([Apple Developer Forums 771999](https://developer.apple.com/forums/thread/771999)). 사용자에게는 집 LAN에 항상 켜진 장치가 없으므로 "검색은 언제나, 원문 가져오기는 기기가 깨어 있을 때"를 전제로 설계해야 한다.

| 기준 | 중앙 집중 푸시 | P2P 동기화 + 기기별 색인 | 연합형 (메타데이터·임베딩만 중앙) |
|---|---|---|---|
| 대표 사례 | Khoj, Open WebUI + oikb, Basic Memory Cloud | Basic Memory 로컬 + git/Syncthing, Smart Connections | Spacedrive v2(베타 전), Tailscale Aperture(상용) |
| 기기가 잠들 때 | 검색·원문 모두 가능 | 각 기기가 자기 사본으로 처리 | 검색은 가능, 원문은 발췌·캐시로 대체 |
| 2GB VPS 적합성 | 서버 쪽 임베딩·파싱 때문에 부적합 | VPS는 불필요하지만 claude.ai용 허브는 따로 필요 | 기기에서 임베딩하면 허브는 100MB 미만(추정) |
| 충돌 | 최신 파일 우선 | git 병합 충돌 또는 `.sync-conflict` 파일 | 원본을 복사하지 않으므로 내용 충돌 없음 |
| 프라이버시 | 모든 평문이 VPS에 | 가장 좋음 (GitHub는 제3자 사본) | 메타데이터·발췌·임베딩만 VPS에 |
| 아이폰의 역할 | 불안정한 업로더 | 약한 피어 | 클라이언트 + 업로더 |
| 움직이는 부품 | 적음 | 적음 | 가장 많음 |

그래서 결론은 데이터 층마다 다른 계열을 쓰는 하이브리드다.

**A층(마크다운 메모리 저장소)**은 작고 가치가 높으며, AI가 쓰고 사람이 고치는 문서다. git이 충돌을 해결하는 층 역할을 한다. 이 층은 사실상 중앙 집중으로 둔다. VPS가 cron이나 GitHub 웹훅으로 `git pull`해 Basic Memory로 색인하면 노트북이 모두 잠들어도 claude.ai 모바일이 최신 기억을 본다. `git diff --name-status <마지막 색인 커밋>..HEAD`는 기기가 오래 오프라인이었어도 정확한 변경 목록을 준다.

**B층(맥·윈도우의 문서, PDF, 프로젝트 폴더)**은 연합형으로 둔다.

**C층(자주 쓰는 소수 폴더)**만 선택적으로 VPS에 고정 캐시해, 잠든 기기 문제를 줄인다.

## 한국어 검색 품질은 제품이 아니라 임베딩과 형태소 분석이 결정한다

조사한 도구 대부분은 기본 임베딩이 영어 전용이다. Khoj는 `gte-small`, Basic Memory는 `bge-small-en-v1.5`, Supermemory 로컬 모드는 `bge-base-en-v1.5`를 쓴다. qmd의 기본 EmbeddingGemma는 README에 CJK 지원이 "제한적"이라고 적혀 있다 ([qmd README](https://github.com/tobi/qmd), [Basic Memory docs](https://docs.basicmemory.com/concepts/semantic-search)).

사용자는 이미 Basic Memory의 임베딩을 `paraphrase-multilingual-MiniLM-L12-v2`로 바꿔 두었다. 한국어가 포함된 Basic Memory 자체 벤치마크에서도 이 모델은 기본값 BGE-small보다 낫다. MRR@10은 0.768→0.868, 교차 언어 recall@5는 0.857→1.0으로 올랐고, 부정 질의 오탐은 0.75→0.0으로 줄었다 ([benchmark](https://github.com/basicmachines-co/basic-memory/blob/main/docs/multilingual-embedding-benchmark.md)). 그러나 같은 벤치마크에서 긴 노트의 청크 경계 recall@5는 0.0이었고, 유사도 컷오프 0.55가 일부 CJK 질의를 걸러 냈다. 또 FastEmbed 0.8.0이 이 모델의 풀링 방식을 바꿨으므로 모델과 버전을 함께 고정하라고 경고한다.

한국어 특화 모델과 비교하면 격차는 더 크다. AutoRAG 한국어(금융) 벤치마크에서 MiniLM의 top-1 F1은 약 0.30으로, KoE5 0.69나 BGE-m3-ko 0.75에 크게 못 미친다 ([AutoRAG benchmark](https://github.com/Marker-Inc-Korea/AutoRAG-example-korean-embedding-benchmark)). MiniLM 수치는 검색 요약으로만 확인돼 재검증이 필요하지만, 어느 쪽으로 기우는지는 분명하다.

MTEB-ko 수치는 KURE와 dragonkue 모델 카드에 실린 자체 보고값이다. 두 표의 과제 구성이 달라 같은 모델도 숫자가 다르다(snowflake-ko는 0.740과 0.765).

권장 방식은 **같은 모델을 쓰되 문서 임베딩은 맥(Metal)에서, 질의 임베딩만 VPS에서 계산하는 것**이다. 첫 후보는 Ollama로 바로 돌릴 수 있는 bge-m3다. 품질을 우선한다면 KURE-v1을 쓰되 ONNX/GGUF 경로부터 검증한다. 1024차원 벡터를 int8로 저장하면 5만 청크가 약 51MB(float32면 약 205MB)라, 별도 ANN 인덱스 없이 sqlite-vec 브루트포스 KNN으로 충분하다. 20토큰 안팎의 질의 하나는 1 vCPU에서 0.2~0.5초가 걸릴 것으로 추정되어 대화형으로 쓰기에 무리가 없다(추정, 실측 필요).

다만 RAM이 빠듯하다. 568M 모델은 fp16으로 약 1.1GB, int8 ONNX로 약 0.6GB를 쓸 것으로 추정된다. Basic Memory의 MiniLM이 이미 RSS 약 0.67GB를 쓰고 있어, 둘을 함께 띄우면 2GB 안에서 OS·프록시와 메모리를 다툰다. 따라서 2단계에서 노트 검색까지 허브의 같은 모델로 통합해 임베딩 모델을 하나만 상주시키거나, VPS를 4GB로 올리는 선택지를 열어 둬야 한다. 임베딩을 외부 API로 넘기면(Basic Memory는 OpenAI 공급자를 지원한다) RAM 문제는 사라지지만, 노트 내용이 제3자에게 전송된다.

키워드 검색에는 더 근본적인 함정이 있다. SQLite FTS5의 `unicode61` 토크나이저는 공백 사이의 문자열 전체를 하나의 토큰으로 삼기 때문에 "검색엔진을" 같은 어절이 통째로 색인된다. `trigram` 토크나이저는 3글자 미만 부분 문자열을 아예 매칭하지 않아 "회의"나 "보험" 같은 2음절 명사를 찾지 못한다 ([SQLite FTS5](https://www.sqlite.org/fts5.html)). Basic Memory와 qmd 모두 한국어 형태소 처리에 대한 문서가 없다.

해법은 색인기에서 Kiwi(kiwipiepy)로 형태소를 분리해 공백으로 이은 별도 FTS 열을 두고, 질의도 같은 방식으로 토큰화하는 것이다. Kiwi는 "금융보험"을 ["금융", "보험"]으로 나눠 BM25가 "보험"으로도 찾게 해 준다. 한국어 LangChain 튜토리얼이 `KiwiBM25Retriever`를 쓰는 이유다 ([WikiDocs](https://wikidocs.net/251980)). Recoll이 한국어 처리를 외부 분석기 python-mecab-ko에 맡긴 것도 같은 결론이다 ([Recoll](https://www.recoll.org/pages/recoll-korean.html)).

SQLite를 고집하지 않는다면 LanceDB(`lindera/ko-dic`)나 Qdrant 1.15 이상(다국어 토크나이저)에 한국어 분석이 내장돼 있다 ([LanceDB FTS](https://docs.lancedb.com/search/full-text-search.md), [Qdrant 1.15](https://qdrant.tech/blog/qdrant-1.15.x/)). 반면 Meilisearch는 한국어 분할 처리량이 약 2MiB/s로 가장 느린 등급이다 ([charabia](https://docs.rs/crate/charabia/latest)). Typesense의 내장 ML 모델은 RAM을 2~6GB 더 요구한다 ([Typesense](https://typesense.org/docs/guide/system-requirements.html)).

키워드 검색과 벡터 검색 결과는 RRF로 합친다. 재순위기의 효과는 분명하다. 한국어 금융 벤치마크의 top-1 F1은 bge-reranker-v2-m3-ko 0.912, 기본 bge-reranker-v2-m3 0.877, jina-reranker-v2 0.807이다 ([dragonkue reranker](https://huggingface.co/dragonkue/bge-reranker-v2-m3-ko)). Basic Memory 0.23의 재순위 옵션은 자체 평가에서 MRR을 0.616→0.719로 올렸다 ([v0.23](https://docs.basicmemory.com/whats-new/v0-23)). 하지만 0.6B 교차 인코더가 후보 20개를 읽으면 1 vCPU에서 수십 초가 걸릴 것으로 추정된다. 그래서 VPS에서는 상위 5~10개만 재순위하거나 생략하고, 재순위는 맥에서 도는 로컬 클라이언트용으로 2단계 이후에 붙인다. jina 재순위기는 CC-BY-NC 라이선스라 업무에 쓰지 않는다.

청크는 qmd나 Basic Memory처럼 문서 구조를 먼저 따라 자른다. 순서는 이렇다. 마크다운 제목(그리고 docling·markitdown이 PDF·Office에서 뽑아낸 제목)으로 먼저 나눈다. 그다음 Kiwi 문장 분리기로 300~600 모델 토큰, 10~15% 겹침의 창을 만든다. 각 청크 앞에는 문서 제목과 제목 경로를 붙인다. Basic Memory는 900자 기준을 쓰지만, 한국어는 같은 글자 수에 담긴 의미가 영어보다 많아 토큰 기준이 더 일관된다(비율은 미검증).

해시는 파일 단위 `file_hash`와 청크 단위 `chunk_hash`를 함께 둔다. `chunk_hash`에는 정규화한 청크 텍스트, 모델 ID, 접두어를 포함시켜, 모델을 바꿀 때만 통제된 전체 재임베딩이 일어나게 한다. 스캔한 PDF와 이미지는 맥에서는 docling의 `ocrmac`(Apple Vision `ko-KR`)으로, 윈도우에서는 PP-OCRv5 한국어 모델(자체 데이터셋 인식 정확도 88.0%)로 처리한다. HWP/HWPX는 kordoc으로 변환한다 ([PaddleOCR](https://www.paddleocr.ai/latest/en/version3.x/algorithm/PP-OCRv5/PP-OCRv5_multi_languages.html), [kordoc](https://dev.co/ai/mcp/kordoc)).

## 아이폰은 색인기가 될 수 없고, 맥·윈도우는 깨어 있을 때 밀어 넣는다

### 아이폰: 조회 클라이언트이자 가끔 쓰는 업로더

**iOS는 서드파티 앱이 백그라운드에 상주하며 파일을 색인하도록 허용하지 않는다.** 우선 실행 시간이 보장되지 않는다. `BGProcessingTaskRequest`로 "몇 분이 걸릴 수 있는 처리 작업"을 요청하고 전원 연결을 조건으로 걸 수는 있지만, 언제 실행될지는 보장하지 않는다 ([Apple](https://developer.apple.com/documentation/backgroundtasks/bgprocessingtaskrequest)). iOS 26의 `BGContinuedProcessingTask`는 사용자가 포그라운드에서 직접 시작해야 하고, 진행 상황이 라이브 액티비티로 표시되며, 사용자가 취소할 수 있고, 자원이 부족하면 시스템이 갑자기 종료할 수 있다 ([Apple](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtask)).

접근할 수 있는 파일도 제한된다. 앱 샌드박스 밖의 파일은 사용자가 문서 선택기로 한 번 고른 폴더만 보안 범위 북마크로 접근할 수 있고, 사용자는 설정에서 언제든 권한을 거둘 수 있다 ([Apple](https://developer.apple.com/documentation/uikit/providing-access-to-directories)). 사진은 파일이 아니라 별도 권한 영역에 있다. 동기화 앱도 같은 벽에 막힌다. Möbius Sync는 안정화된 뒤에도 하루 1~2시간만 동기화되고, 처음 동기화가 시작되기까지 24시간이 걸릴 수 있다고 밝힌다 ([FAQ](https://mobiussync.com/faq/)). 시스템 색인을 외부에서 조회할 길도 없다. iOS 18의 `IndexedEntity`는 앱이 Spotlight 의미 색인에 *쓰는* 쪽만 열어 줄 뿐, 외부 에이전트가 아이폰의 시스템 색인을 조회하는 공개 API는 없다 ([Apple](https://developer.apple.com/documentation/appintents/indexedentity)).

그래서 아이폰에는 두 가지 역할만 맡긴다. 읽기는 claude.ai iOS 앱이 VPS 커넥터로 처리한다. claude.ai 웹에서 추가한 커넥터는 모바일 앱에 그대로 동기화된다. 쓰기는 공유 시트 단축어("색인으로 보내기")가 VPS의 수집 엔드포인트로 POST하거나, Working Copy가 메모 저장소에 커밋·푸시하는 방식이다. iOS 26의 개인 자동화는 시간대나 충전기 연결 같은 트리거에서 묻지 않고 실행되도록 설정할 수 있다 ([Apple Shortcuts](https://support.apple.com/en-ca/guide/shortcuts/apd690170742/9.0/ios/26)). 다만 잠금 상태에서는 실패한다는 오래된 보고가 있어, 자동 실행은 최선 노력으로만 기대한다. 업로더가 공개 HTTPS와 기기 토큰을 쓰면 아이폰에서 Tailscale을 상시 켜 둘 필요가 없다.

### 윈도우: 새 파일명 색인을 만들지 말고 Everything을 재사용한다

파일명 색인은 Everything에 맡긴다. Everything은 NTFS 변경 저널로 거의 즉시 갱신되는 파일명 색인을 유지하고, `es.exe -json`, `dm:today` 같은 질의, 1.5 버전의 `-from-journal-pos` 저널 옵션을 제공한다 ([voidtools](https://www.voidtools.com/support/everything/command_line_interface/)). 내장 HTTP 서버는 Basic 인증만 있고 TLS가 없으므로 `127.0.0.1`에만 바인딩한다 ([voidtools HTTP](https://www.voidtools.com/support/everything/http/)). 내용 변경 감지는 USN 변경 저널이 정석이다. `ReadDirectoryChangesW`는 앱이 항상 실행 중이어야 하고 파일이 많으면 시스템 성능을 떨어뜨리지만, 저널은 꺼져 있던 동안의 변경을 볼륨 전체 재색인 없이 따라잡게 해 준다 ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/fileio/change-journals)).

가장 흔한 사고는 **OneDrive 자리표시자**에서 난다. `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`(0x00400000)나 `RECALL_ON_OPEN`(0x00040000) 속성이 있는 파일을 읽으면 클라우드에서 다운로드가 시작된다 ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/fileio/file-attribute-constants)). 그래서 에이전트는 이 속성이 있는 파일의 메타데이터만 기록한다. Windows Search 색인기가 실제로 이런 다운로드를 일으킨 사례도 보고됐다 ([Tech Community](https://techcommunity.microsoft.com/discussions/onedriveforbusiness/onedrive-files-on-demand-onedrivewindows11-automatically-downloads-vhdx-files-fr/4151433)). 에이전트는 WSL이 아닌 네이티브 프로세스여야 NTFS와 USN 저널을 직접 볼 수 있고, 서비스보다 로그온 시 실행되는 작업 스케줄러 작업으로 두는 편이 사용자의 OneDrive 매핑을 보기 쉽다(추론).

윈도우에 내장된 AI 기능은 아직 기댈 곳이 못 된다. Recall은 서드파티가 스냅숏을 읽을 API가 없고 내보내기는 EEA에서만 지원돼 한국에서는 데이터 원천이 될 수 없다 ([Microsoft Support](https://support.microsoft.com/en-US/Windows/Ai/Ai-Features/export-recall-snapshots)). Windows MCP의 File Explorer 커넥터는 `search_files`, Office·PDF 텍스트 읽기, Copilot+ PC에서의 자연어 의미 검색을 제공하지만 프리뷰 단계이고 그 PC 안에서만 동작한다 ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/ai/mcp/file-connector)). 덧붙여 윈도우의 Claude Code에서 `npx` 기반 stdio MCP 서버를 쓰려면 `cmd /c npx`로 감싸서 등록해야 한다 ([Claude Code MCP](https://code.claude.com/docs/en/mcp)).

### 맥: FSEvents 이벤트 ID와 TCC 권한이 설계를 좌우한다

FSEvents는 볼륨마다 영속 데이터베이스에 이벤트를 저장하고, 이벤트 ID가 재부팅 후에도 계속 증가함을 보장한다. 그래서 마지막 이벤트 ID와 볼륨 UUID를 저장해 두면 잠자기나 재부팅 뒤에도 `sinceWhen`부터 따라잡을 수 있다 ([Apple FSEvents](https://developer.apple.com/library/mac/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html)). iCloud "Mac 저장 공간 최적화"로 로컬에서 비워진 파일은 `st_flags`에 `SF_DATALESS`가 켜져 있지만 크기는 원래 크기로 보이므로, 이 플래그를 확인하지 않고 읽으면 다운로드가 일어난다 ([Eclectic Light](https://eclecticlight.co/2024/03/18/how-icloud-drive-works-in-macos-sonoma/)).

TCC 권한은 운영상 가장 자주 발목을 잡는다. launchd 에이전트가 `~/Documents`, `~/Desktop`, iCloud Drive를 읽으려면 보호 폴더 밖의 고정 경로에 둔 바이너리에 전체 디스크 접근 권한(FDA)을 한 번 부여해야 한다. 버전마다 바이너리 경로가 바뀌면 업데이트할 때마다 권한이 사라지는데, Claude Code 자체에서도 이런 문제가 보고됐다 ([claudeissues #74234](https://claudeissues.com/issue/74234-macos-full-disk-access-tcc-prompts-reappear-on-every-auto-update-per-version-bin)). Spotlight의 `mdfind`는 경로만 돌려주므로 후보를 찾는 데만 쓰고, 내용은 직접 추출한다.

### 세 기기에 공통으로 적용할 원칙

공통 원칙은 실제로 운영 중인 동기화 도구에서 그대로 빌려 온다. 파일시스템 감시자와 주기적 전체 재스캔을 짝지운다(Syncthing은 시간당 한 번 재스캔한다). mtime과 크기로 먼저 거른 뒤 BLAKE3나 SHA-256으로 해시한다. `.git/`, `.sync-conflict-*`, SQLite 파일, 클라우드 자리표시자는 제외한다 ([Syncthing](https://docs.syncthing.net/users/syncing.html), [Spacedrive](https://github.com/spacedriveapp/spacedrive)).

| 기기 | 역할 | 변경 감지 | 재사용할 OS 색인 | 핵심 함정 |
|---|---|---|---|---|
| 맥북 (애플 실리콘) | 주 임베딩 계산기 + 원문 제공자 | FSEvents 이벤트 ID + 일일 재스캔 | Spotlight `mdfind` | TCC/FDA, `SF_DATALESS`, WoL 불가 |
| 윈도우 랩톱 | 원문 제공자 + 자체 증분 임베딩 | USN 저널 또는 Everything 저널 + 야간 재스캔 | Everything `es.exe -json` | OneDrive `RECALL_ON_*`, TLS 없는 HTTP 서버 |
| 아이폰 | 조회 클라이언트 + 가끔 쓰는 업로더 | 없음 (단축어·Working Copy 트리거) | 접근 불가 | 백그라운드 실행 비보장 |
| VPS | 공개 허브 + 질의 임베딩 + A층 색인 | GitHub `git pull` + diff | 해당 없음 | RAM 2GB, 1 vCPU |

## 공개 OAuth 엔드포인트 하나로 다섯 클라이언트가 모두 접근한다

claude.ai는 웹·데스크톱·모바일 모두 사용자 기기가 아니라 Anthropic 클라우드에서 원격 MCP 서버에 접속한다. 공식 도움말은 서버가 "Anthropic IP 대역에서 공개 인터넷으로 도달 가능해야" 하며, 사설망이나 VPN 뒤의 서버는 연결되지 않는다고 명시한다 ([Claude Help Center](https://support.claude.com/en/articles/11175166-getting-started-with-custom-connectors-using-remote-mcp)). 제3자 분석에 따르면 커넥터 검증은 사설·CGNAT·루프백·링크 로컬 주소를 거부하고 IPv4만 지원한다 ([Zuplo](https://zuplo.com/learn/mcp/errors/mcp-server-works-in-claude-code-but-not-claude-ai)). 따라서 Tailscale 노드 주소(100.64.0.0/10)를 그대로 등록할 수 없다.

Anthropic의 MCP 터널은 사설망의 MCP 서버를 아웃바운드 연결로 노출하는 공식 기능이다. 하지만 Enterprise 플랜 조직이 신청해야 쓸 수 있는 리서치 프리뷰이고, 기본적으로 RFC 1918 사설 대역으로만 프록시한다 ([Claude docs: MCP tunnels](https://claude.com/docs/connectors/mcp-tunnels/overview)). 개인 계정에는 해당하지 않는다. 결국 **사용자가 이미 만든 VPS의 공개 HTTPS 엔드포인트가 유일한 정문**이고, 기기 엔드포인트는 그 뒤 tailnet 안에만 둔다.

### 정문이 갖춰야 할 인증 조건

이 정문의 조건은 MCP 인증 명세(2025-11-25)와 Anthropic 커넥터 문서가 정한다. 명세상 필수 요건은 OAuth 2.1, 보호 리소스 메타데이터(RFC 9728), S256 PKCE, 토큰 대상(audience) 검증, 토큰 패스스루 금지다. 클라이언트 등록은 사전 등록, CIMD, DCR 순서로 시도된다 ([MCP spec](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)).

Claude 쪽에는 추가 조건이 있다. `WWW-Authenticate: Bearer resource_metadata=…` 헤더는 401 응답에 있을 때만 인식하고 200 응답에 붙은 것은 무시한다. `authorization_servers` 목록에서는 첫 번째 항목만 쓴다. 발견·등록·토큰 엔드포인트에는 **10초**, 토큰 갱신에는 30초의 제한 시간을 두고, `client_credentials` 방식은 지원하지 않는다. 고정 헤더 자격 증명은 일부 조직 대상 베타라 개인 Pro/Max 계정은 기댈 수 없다 ([Claude docs: Authentication](https://claude.com/docs/connectors/building/authentication)). 리디렉션 URI는 호스팅 앱용 `https://claude.ai/api/mcp/auth_callback`과, Claude Code용으로 포트를 가리지 않는 루프백 주소다 ([Claude docs: Build](https://claude.com/docs/connectors/building)).

mcp-auth-proxy README는 Claude 웹·데스크톱, Claude Code, ChatGPT 웹·데스크톱을 검증된 클라이언트로 명시한다. Google·GitHub·OIDC 공급자를 지원하고, 사용자를 정확한 값이나 글롭 패턴으로 매칭할 수 있다 ([mcp-auth-proxy](https://github.com/sigbit/mcp-auth-proxy)). 다만 README에는 DCR, RFC 9728, PKCE에 대한 언급이 없다. 0단계에서 실제 401 응답 헤더와 1 vCPU에서의 토큰 응답 시간을 직접 확인해야 한다.

### 도구 설계는 가장 엄격한 클라이언트에 맞춘다

검색과 원문 가져오기는 나눈다. 검색 도구는 원문 대신 짧은 발췌, 점수, 문서 ID를 페이지 단위로 돌려주고, 원문은 별도의 `fetch(id, offset, length)`로 가져오게 해서 Claude Code의 25k 토큰과 Codex의 60초 안에 끝나게 한다. 도구 수는 `search`, `fetch`, `list_devices`(기기별 `last_seen` 포함), `index_status` 정도로 적게 유지한다. 커뮤니티 보고에 따르면 입력 스키마가 16KiB를 넘는 도구는 claude.ai가 조용히 누락시킨다 ([claudeissues #77296](https://claudeissues.com/issue/77296-bug-claude-ai-connector-ingestion-silently-drops-any-tool-with-inputschema-16-38)). 노트 쓰기는 Basic Memory 도구에 맡겨, 모든 쓰기가 git 이력에 남아 나중에 검토할 수 있게 한다.

맥·윈도우에서 도는 로컬 클라이언트(Claude Code, Codex, Aside)는 공개 경로 대신 VPS의 tailnet 주소(Tailscale Serve)로 붙어 지연을 줄인다. 그러면 공개 포트를 Anthropic 대역으로 좁힐 수 있다. ChatGPT도 함께 쓰려면 OpenAI 송신 대역을 열어야 하는데, 그 범위는 조사하지 못했다.

## 모든 기기를 읽는 허브는 가장 강력한 유출 도구가 된다

연합형은 중앙 집중형보다 VPS에 남는 데이터가 적지만, 위험이 사라지지는 않는다. VPS에는 경로, 파일명, 발췌, 임베딩이 쌓인다. 임베딩으로도 의미 내용이 새어 나갈 수 있으니 민감 데이터로 다뤄야 한다.

더 큰 위험은 허브가 하는 일 자체에 있다. 모든 기기의 파일을 읽을 수 있는 집약 MCP는 프롬프트 인젝션이 성공하는 순간 곧바로 유출 도구가 된다. 색인된 웹 문서, 메일, PDF에는 신뢰할 수 없는 지시문이 섞여 있을 수 있다. 같은 대화에 로그인된 사이트를 조작하는 Aside 브라우저 에이전트처럼 외부로 내보낼 수단까지 있으면, "개인 데이터 접근, 신뢰할 수 없는 입력, 외부 통신"이라는 세 조건이 한자리에 모인다.

방어는 네 겹으로 쌓는다.

**네트워크 층.** VPS에 `tag:hub` 태그를 붙이고, `tag:hub`에서 기기 에이전트 포트로 가는 연결만 허용하며, 기기끼리의 통신은 막는다. 기기 엔드포인트는 tailnet IP에만 바인딩하고 Funnel로 공개하지 않는다. Taildrive를 쓴다면 `drive:share`/`drive:access` 속성과 grant로 공유 폴더를 최소한으로 좁힌다 ([Taildrive](https://tailscale.com/kb/1369/taildrive)).

**인증 층.** mcp-auth-proxy의 비밀번호 로그인을 GitHub나 Google OIDC로 바꾸고, 사용자를 정확한 값으로 매칭한다. MCP 명세가 금지하는 대로 claude.ai의 토큰을 기기에 전달하지 않는다 ([MCP spec](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)). 허브가 기기를 호출할 때는 tailnet 신원이나 기기별로 따로 둔 비밀로 인증한다. 예를 들어 `X-Tailscale-User`·`X-Tailscale-Node` 헤더를 넘겨주는 프록시 패턴을 쓸 수 있다 ([tailscale-mcp-proxy](https://github.com/jaxxstorm/tailscale-mcp-proxy)).

**도구 층.** 기기 엔드포인트는 읽기 전용으로 둔다. 경로 허용 목록과 거부 패턴(`~/.ssh`, `.env`, `*.pem`, 키체인, 브라우저 프로필, 비밀번호 관리자 내보내기 파일)은 에이전트 쪽에서 강제한다. nextcloud-mcp-server의 `EXCLUDED_TAGS`처럼, "민감" 태그가 붙은 파일은 카탈로그에서 아예 뺀다 ([nextcloud-mcp-server](https://github.com/cbcoutinho/nextcloud-mcp-server)). 쓰기는 Basic Memory를 거친 git 커밋만 허용해 사후 검토가 가능하게 한다.

**운영 층.** 모든 `fetch` 호출을 기기, 경로, 클라이언트와 함께 기록한다. 결과 크기에 상한을 두고, 클라이언트의 도구별 승인 기능은 끄지 않는다. 맥에서는 FDA를 에이전트의 고정 바이너리에만 준다. Apple이 2026년에 AI 에이전트의 FDA를 제한한다는 보도는 확인되지 않았으므로, macOS 업데이트 때마다 다시 확인한다.

방화벽은 공개 포트를 Anthropic 송신 대역 `160.79.104.0/21`로 좁힐 수 있다. 공식 페이지가 34.162.x 주소를 "단계적 폐지"로 표시하고 있으므로 이 대역을 기준으로 삼는다 ([Anthropic IP](https://platform.claude.com/docs/en/api/ip-addresses)). 이 제한은 로컬 클라이언트를 tailnet 경로로 돌려야 성립하고, ChatGPT를 쓰면 예외가 생긴다.

그 밖에 기억해 둘 점이 세 가지 있다. 비공개 GitHub 저장소도 결국 제3자가 가진 사본이다. Everything HTTP 서버는 TLS가 없으니 로컬호스트 밖으로 노출하지 않는다. mcp-auth-proxy는 마지막 릴리스가 2026년 5월이라 유지보수가 둔화되는지 지켜봐야 한다 ([mcp-auth-proxy](https://github.com/sigbit/mcp-auth-proxy)).

## 여섯 단계로 쌓되, 한국어 품질 검증을 파일 확장보다 먼저 한다

순서의 원칙은 이미 있는 것을 먼저 검증하고, 가장 가치가 큰 노트 검색 품질을 올린 다음, 파일로 넓히는 것이다. 각 단계는 다음 단계가 없어도 그 자체로 쓸모가 있도록 나눴다.

| 단계 | 할 일 | 차용 부품 | 완료 기준 |
|---|---|---|---|
| 0. 정문 점검 | mcp-auth-proxy의 401 + `resource_metadata`, DCR, claude.ai 콜백·루프백 리디렉션, 10초 이내 토큰 응답 확인. claude.ai 웹·iOS, Claude Code, Codex, Aside에서 연결 테스트. VPS가 cron이나 웹훅으로 메모 저장소를 `git pull`해 Basic Memory를 갱신. FastEmbed와 모델 버전 고정, 스왑 설정 | Basic Memory, mcp-auth-proxy | 노트북이 모두 꺼진 상태에서 아이폰 claude.ai가 오늘 쓴 노트를 찾음 |
| 1. 사설망 | VPS·맥·윈도우에 Tailscale 설치(무료 Personal 플랜은 사용자 소유 기기 수 제한 없음, [CostBench](https://costbench.com/software/business-vpn/tailscale/free-plan)), `tag:hub` ACL, 로컬 클라이언트용 Tailscale Serve 경로, 공개 포트를 Anthropic 대역으로 제한, OIDC 로그인 전환 | Tailscale | 기기끼리 직접 통신이 막힌 것을 확인하고, 로컬 Claude Code가 tailnet 경로로 접속 |
| 2. 한국어 품질 | 허브 v0 구축: 메모 저장소만 Kiwi 형태소 FTS5 + sqlite-vec(bge-m3 또는 KURE-v1, 임베딩은 맥에서) + RRF로 색인. 내 노트에서 뽑은 한국어 질의 30~50개로 Basic Memory 검색과 비교 | qmd 설계, sqlite-vec, Kiwi, Ollama | 자체 평가 세트에서 MRR과 recall@5 개선을 확인한 뒤, VPS에 상주하는 모델을 하나로 정리 |
| 3. 맥 에이전트 | FSEvents + 일일 재스캔, `SF_DATALESS` 파일 건너뛰기, markitdown·docling(ocrmac)·kordoc으로 추출, 청크 분할·임베딩 후 허브로 푸시, tailnet 전용 읽기 전용 `fetch` | markitdown, docling, kordoc, (대안) Taildrive | 맥 문서 폴더를 검색하고 원문을 가져옴. 맥이 잠들어 있으면 "오프라인, 마지막 접속 T"와 발췌를 반환 |
| 4. 윈도우 에이전트 | 로그온 시 실행되는 작업 스케줄러 작업, Everything 저널이나 USN으로 변경 감지, OneDrive 자리표시자 건너뛰기, 증분 임베딩은 로컬에서 처리하고 초기 대량분은 맥의 작업 큐로 넘기는 선택지 | Everything `es.exe`, markitdown, PP-OCRv5 | OneDrive 다운로드를 일으키지 않고 윈도우 폴더를 색인 |

| 6. 운영·확장 | 파일별 색인 상태 도구, 감사 로그, 백업, 맥 로컬용 재순위(bge-reranker-v2-m3-ko), ChatGPT 연결(선택), Spacedrive v2 베타 평가 | Basic Memory 재순위, Spacedrive v2 | 기기·폴더별 색인 범위와 최신성이 도구로 확인됨 |

2단계를 파일 확장보다 앞에 둔 이유는 위험과 효과의 차이 때문이다. 노트는 이미 모든 클라이언트가 쓰는 핵심 코퍼스이고, 모델 교체와 형태소 열 추가는 새 기기 에이전트 없이 VPS와 맥만으로 끝난다. 반면 파일 확장은 TCC, OneDrive, 잠든 기기 같은 운영 문제를 함께 끌고 온다.

6단계의 색인 상태 도구는 Khoj 사용자들이 겪은 불편을 처음부터 피하려는 것이다. Khoj 사용자들은 파일별 동기화 상태와 색인 범위를 볼 수 없다고 불평했다 ([Khoj #1363](https://github.com/khoj-ai/khoj/issues/1363)).

VPS RAM도 미리 계산해 둬야 한다. Basic Memory의 MiniLM 상주분(약 0.67GB)과 허브의 질의 임베더(int8 약 0.6GB, 추정)를 합치면, OS와 프록시까지 더해 2GB가 거의 찬다. 2단계에서 모델을 하나로 합치지 못하면 4GB 플랜으로 옮기는 것이 가장 단순한 해법이다.

> **참고 영상**: 영상 없음. 이 단계 계획은 사용자 환경에 맞춘 조합이라 그대로 대응하는 공식 데모가 없다. 각 단계의 개념 영상은 앞 섹션에 있다.

## 결론

이번 조사로 바뀐 관점이 있다. 설계의 실제 단위는 "색인을 어디에 두는가"보다 "임베딩을 어디서 계산하고, 공개 정문을 누가 맡는가"라는 점이다. claude.ai가 클라우드에서 접속한다는 사실 하나가 VPS를 유일한 공개 정문으로 확정한다. 그 덕분에 나머지, 즉 기기 엔드포인트, 원본 파일, 무거운 임베딩·OCR·재순위는 전부 사설망과 맥 안에 둘 수 있다. 1 vCPU/2GB VPS는 약점이라기보다 역할의 경계선이다. 질의 임베딩, SQLite 카탈로그, OAuth 정문만 맡기면 충분하다. 그 이상을 올리려는 순간 Khoj나 Immich처럼 4~12GB를 요구하는 제품군으로 넘어간다. 아이폰 문제도 같은 방식으로 풀린다. 아이폰을 색인 피어가 아니라 클라이언트로 정의하면 iOS 백그라운드 제약은 설계 문제가 아니게 된다.

남은 불확실성은 실측으로만 풀 수 있다. 1 vCPU에서의 실제 질의 임베딩 지연, KURE-v1의 ONNX/GGUF 이식 가능성, Aside 커스텀 MCP의 OAuth 세부 동작, mcp-auth-proxy의 DCR·RFC 9728 지원 여부가 그것이다. 또 2026년 11월에 나올 Spacedrive v2 베타가 윈도우와 원격 MCP를 지원하면, 직접 만든 기기 에이전트는 언제든 바꿔 끼울 수 있는 임시 부품이 된다. 지금 직접 만드는 층을 얇게 유지해야 하는 이유가 바로 이것이다.
